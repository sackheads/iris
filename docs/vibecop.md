# Vibecop Guardian

Moved from the feature tour ([docs/features.md](features.md)), word for word, with the two duplicate entries merged (#534).

Iris includes a reimplementation of [**Vibecop**](https://github.com/bnaylor/vibecop), an independent, paranoid AI guardian (using an auxiliary local model) that, when enabled, evaluates every terminal command or file operation proposed by the primary agent that the "Always allow" rules do not already permit.

*   **Off by default**: Vibecop is a pre-screen, not an approver. With it off (Settings → Vibecop, or the Setup Wizard), nothing pre-screens a call, so every gated command and file operation the allowlist does not already permit asks you — including those of subagents and of the independent goal grader — and so does every gate script `schedule_job` proposes. An event card for a blocked job run shows no verdict, only the **Approve and run** button. One exception for the grader, and it holds whether Vibecop is on or off: a `run_command` that is exactly an executable check you approved when you locked the goal contract (surrounding spaces, tabs and line breaks aside; no prefixes or additions), run in the workspace the goal had when you approved it, runs without asking, because you already approved that command there. It still asks if the agent has since moved the conversation to another workspace, if the check was added or changed through `amend_goal_contract` (you never saw it), or if the check contains a line break or another control character that could hide part of it from you. The grader may also read any file, or list any directory, inside that approved workspace without asking — reads only, for a path written inside the workspace that really lands there, so a `..`, a symlink that leads outside, or a path that only reaches the workspace through a symlink from elsewhere asks. Such a read is opened step by step from the workspace itself without following any symlink, so a symlink swapped in after the check cannot redirect it; the cost is that a read through any symlink in the workspace, even one that points back inside, is refused rather than followed. Writes, every other command, and reads outside the workspace ask, and the main agent and subagents get none of this. Approving a check approves what it runs, as it is when the grader runs it: approving `make test` also approves whatever the Makefile says by then, and the agent can edit the Makefile in the meantime. Background job runs are unaffected: Vibecop or not, a gated call they make that no allowlist rule or grant covers is refused on the spot and lands on the event card.
*   **Auto-Approval, reads only on your Mac**: If Vibecop judges a call routine and safe, it runs without asking, saving you from prompt fatigue. On your Mac (not in the sandbox VM) that holds only for a call that can only read: a file read, or a command a fixed, conservative check recognises as read-only. That means one of a few programs (`ls`, `cat`, `head`, `tail`, `wc`, `grep`, `rg`, `find`, `file`, `stat`, `du`, `df` and the like), with only options on that program's short list of read-only ones, `find` with tests only, and no redirection, pipe, chaining, substitution, glob or variable. Git always asks: a repository's own config can make even `git status` run a program, and the sandbox VM can write that config. The check also asks when the program would be found through a `PATH` entry that is relative, or inside your home folder or the working directory (so a `PATH` with `~/bin` ahead of `/bin` means prompts), and when the command runs in your home folder itself or above it. Every other host command, and every file write, asks you whatever Vibecop says; it can still refuse one outright. In the sandbox VM, Vibecop approves routine work as before. Once you click **Deny** on a command in a conversation, nothing there runs without asking again until Iris restarts, from Vibecop or the read-only check; your "Always allow" rules still apply, since you set them (#600).
*   **Guardian Mode**: You can run `/vibecop init` in any workspace. The primary agent will analyze your project and generate a custom `.iris/vibecop.md` file. Vibecop uses this as its system prompt, learning what commands are normal *specifically for this project* (e.g., `go build` is safe here, but `npm` should trigger an escalation).
*   **Escalation**: If the command is destructive, touches restricted paths, or isn't listed in the Guardian config, Vibecop blocks it and escalates to a user confirmation dialog.
*   **Model Flexibility**: Vibecop supports multiple backends — embedded `llama.cpp`, `MLX` for Apple Silicon, cloud providers, and local **Ollama** daemons. When Ollama is selected, Iris auto-probes the daemon to discover installed models, offers a model picker, and can pull the recommended `gemma4:12b` directly from the UI. A clear warning banner is shown if the Ollama daemon is not reachable.

## Always allow, and the path a file operation is judged by

Includes "Always allow" and "Always allow in project" persistence. A file operation is asked about, checked against those rules and run by the path it will actually touch: `~` expanded, a relative path joined onto the conversation's workspace (or the app's own directory when there is none), and `..` and symlinks resolved, so a link in the workspace that points elsewhere is shown at its target, and a rule saved in another spelling of the same file still matches. The file is then opened one directory at a time without following any symlink, so if a link has been swapped into that path by the time the tool runs (or by the time you click **Approve and run** on a card), the call is refused rather than followed. For the same reason a write to a dangling symlink is refused, not turned into a file. A path containing a NUL character is refused outright. One consequence for existing rules: an "Always allow" rule saved for a *relative* path no longer matches, because a relative path names no file until it is resolved, so you will be asked once more for those and the new rule is saved as the full path. A project rule's relative path is still read relative to that project.
