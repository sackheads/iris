# Vibecop Guardian

Moved from the feature tour ([docs/features.md](features.md)), word for word, with the two duplicate entries merged (#534).

Iris includes a reimplementation of [**Vibecop**](https://github.com/bnaylor/vibecop), an independent, paranoid AI guardian (using an auxiliary local model) that, when enabled, evaluates every terminal command or file operation proposed by the primary agent that the "Always allow" rules do not already permit.

*   **Off by default**: Vibecop is a pre-screen, not an approver. With it off (Settings → Vibecop, or the Setup Wizard), nothing pre-screens a call, so every gated command and file operation the allowlist does not already permit asks you — including those of subagents and of the independent goal grader — and so does every gate script `schedule_job` proposes, which asks you whether Vibecop is on or off (#687). An event card for a blocked job run shows no verdict, only the **Approve and run** button. One exception for the grader, and it holds whether Vibecop is on or off: a `run_command` that is exactly an executable check you approved when you locked the goal contract (surrounding spaces, tabs and line breaks aside; no prefixes or additions), run in the workspace the goal had when you approved it, runs without asking, because you already approved that command there. It still asks if the agent has since moved the conversation to another workspace, if the check was added or changed through `amend_goal_contract` (you never saw it), or if the check contains a line break or another control character that could hide part of it from you. The grader may also read any file, or list any directory, inside that approved workspace without asking — reads only, for a path written inside the workspace that really lands there, so a `..`, a symlink that leads outside, or a path that only reaches the workspace through a symlink from elsewhere asks. Such a read is opened step by step from the workspace itself without following any symlink, so a symlink swapped in after the check cannot redirect it; the cost is that a read through any symlink in the workspace, even one that points back inside, is refused rather than followed. Writes, every other command, and reads outside the workspace ask, and the main agent and subagents get none of this. Approving a check approves what it runs, as it is when the grader runs it: approving `make test` also approves whatever the Makefile says by then, and the agent can edit the Makefile in the meantime. Background job runs are unaffected: Vibecop or not, a gated call they make that no allowlist rule or grant covers is refused on the spot and lands on the event card.
*   **Auto-Approval, reads only on your Mac**: If Vibecop judges a call routine and safe, it runs without asking, saving you from prompt fatigue. On your Mac (not in the sandbox VM) that holds only for a call that can only read: a file read, or a command a fixed, conservative check recognises as read-only. That means one of a few programs (`ls`, `cat`, `head`, `tail`, `wc`, `grep`, `rg`, `find`, `file`, `stat`, `du`, `df`, `date` with only `-u`, `-R` and a quoted `+FORMAT`, and the like), with only options on that program's short list of read-only ones, `find` with tests only, and no redirection, pipe, chaining, substitution, glob or variable. Git reads (`status`, `diff`, `log`, `show`, `blame`, `rev-parse`, `ls-files`, listing `branch`, `describe`, `shortlog`, with listed options) run without asking only in a repository no sandbox can reach: its git folder, and every folder from where the command runs up to the repository, outside every folder a sandbox can write. A repository's config can make even `git status` run a program, so in a sandbox workspace's own repository, one nested in a sandbox folder, or one the sandbox made, git asks. The read runs on exactly the repository Iris checked, never one git would otherwise discover. Such a read runs exactly as checked plus a fixed neutraliser Iris adds, shown in its result: no shell, attributes taken from the empty tree, and every config key that can run a program (fsmonitor, external diff, textconv and filters, signature checks, the pager) overridden, so your own pager and diff tool don't apply to it. Nor does your global or system git config (`~/.gitconfig`, `/etc/gitconfig` and Homebrew's), so their settings (`diff.algorithm`, `core.quotePath`, colours, `safe.directory`) don't either: output can differ from your Terminal's, and a repository owned by another user errors rather than runs. It needs git 2.40 or later; an older git asks (#607). A read that runs without asking runs exactly as checked: without your shell's startup files (`zsh -f`), with only the system's `PATH` entries (none that is relative, inside your home folder, inside the working directory, or inside any folder a sandbox can write or ever could, kept in Iris's Keychain item so a deleted conversation's workspace or a removed grant still counts (#616), and a host command can't delete or rewrite it (#717); `config/sandbox-writable-roots.jsonl` is a readable copy, and if it's changed outside Iris, Iris says so once and rewrites it), and with almost none of Iris's environment. If Iris can't read that record, no such read runs without asking until it can, and Iris says so once. So a program found only in `~/bin` or a project's `node_modules/.bin` asks, and so does any read run from your home folder itself or above it. Anything you approve yourself runs as it always has, with your own shell setup. Every other host command, and every file write, asks you whatever Vibecop says; it can still refuse one outright. In the sandbox VM, Vibecop approves routine work as before, except in a conversation where you let the sandbox write your home folder or another guarded folder ([Subagent Sandboxing](features.md#subagent-sandboxing)): there the VM is no safe box, so only the same read-only commands run without asking. Once you click **Deny** on a command in a conversation, nothing there runs without asking again until Iris restarts, from Vibecop or the read-only check; your "Always allow" rules still apply, since you set them (#600). Whatever let a call run without asking is said under its pill, and in a copied or exported transcript: Vibecop's reason, the rule that matched (global, this project's, or Iris's own folder), the job run's sandbox grant, a check you approved for the goal, auto-approve in a headless run, or "no approval needed" for a tool that has no approval step. A call you approved yourself adds nothing, since your answer is its record (#599).
*   **Guardian Mode**: You can run `/vibecop init` in any workspace. The primary agent will analyze your project and generate a custom `.iris/vibecop.md` file. Vibecop uses this as its system prompt, learning what commands are normal *specifically for this project* (e.g., `go build` is safe here, but `npm` should trigger an escalation). Writing the file asks you, and its rules take effect once you review and trust them: see the next bullet.
*   **The workspace's `.iris/` is yours to change, not the agent's** (#617): `.iris/vibecop.md`, the project allowlist (`.iris/permissions.json`) and the sandbox setting (`.iris/sandbox.json`) decide what later runs without asking, so a model or tool write into a workspace `.iris/` always asks you, even when Vibecop approves it or an "Always allow" rule covers it, and an unattended run's is refused. So `/vibecop init` costs one approval, then a review: the rules it wrote take effect once you trust them (below). Iris's own writes there (an "Always allow in project" click, a sandbox setting you change) do not ask again. In the sandbox VM, `.iris/` is mounted read-only over the read-write workspace, created empty first if it is missing, so nothing in the VM can write, rename, remove or link over it; a workspace whose `.iris` is a symbolic link or not a folder refuses sandboxed commands until you fix it. Iris reads these files only as plain files with one link, so a symlink or hard link to a file elsewhere in the repository (which the VM could write) is ignored. And Iris uses these files only as it wrote them, or as you trusted them (#625): a file that came with the folder (a cloned repository's own `permissions.json`, say), was edited outside Iris, was written by the agent (even with your approval, which shows the path, not the rules), or was planted in a nested `.iris/` the sandbox could write, is treated as absent. Its rules are off, the sandbox setting is the default, and Vibecop gets no workspace rules. Linking such a workspace says so in the conversation; to turn them on, right-click the conversation and choose **Review Workspace Rules…**, read the files, and click **Trust These Rules**. Iris keeps a fingerprint of each trusted file in its own settings folder (`config/workspace-trust.json` under `~/.iris`), which nothing the agent does unasked can write. **After upgrading**, every workspace's existing `.iris/` rules are untrusted until you review them once, so a project allowlist you rely on stops applying until you do. On your Mac a command is caught when it names a workspace `.iris` (best effort: a script or glob can reach a path it does not spell), which is why the VM side is a mount.
*   **Escalation**: If the command is destructive, touches restricted paths, or isn't listed in the Guardian config, Vibecop blocks it and escalates to a user confirmation dialog.
*   **Model Flexibility**: Vibecop supports multiple backends — embedded `llama.cpp`, `MLX` for Apple Silicon, cloud providers, and local **Ollama** daemons. When Ollama is selected, Iris auto-probes the daemon to discover installed models, offers a model picker, and can pull the recommended `gemma4:12b` directly from the UI. A clear warning banner is shown if the Ollama daemon is not reachable. With **Cloud**, Vibecop runs on your primary provider: on the model you set in Settings → Vibecop → Cloud Model, or, left empty (the default), on your easy tier's model, which Settings shows as the effective model. Settings warns when the name does not look like your primary provider's, and a model the provider does not have falls back to the easy tier for that check, with one notice the first time (#620). Tier 3's Cloud engine reads the same Cloud Model, whichever engine Vibecop uses ([guard design](prompt_injection_guard_design.md#tier-3-auxiliary-model-classifier-probe-implemented), #800).

## Always allow, and the path a file operation is judged by

Includes "Always allow" and "Always allow in project" persistence. A file operation is asked about, checked against those rules and run by the path it will actually touch: `~` expanded, a relative path joined onto the conversation's workspace (or the app's own directory when there is none), and `..` and symlinks resolved, so a link in the workspace that points elsewhere is shown at its target, and a rule saved in another spelling of the same file still matches. The file is then opened one directory at a time without following any symlink, so if a link has been swapped into that path by the time the tool runs (or by the time you click **Approve and run** on a card), the call is refused rather than followed. For the same reason a write to a dangling symlink is refused, not turned into a file. A path containing a NUL character is refused outright. One consequence for existing rules: an "Always allow" rule saved for a *relative* path no longer matches, because a relative path names no file until it is resolved, so you will be asked once more for those and the new rule is saved as the full path. A project rule's relative path is still read relative to that project.
