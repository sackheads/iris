# Vibecop Guardian

Moved from the feature tour ([docs/features.md](features.md)), word for word, with the two duplicate entries merged (#534).

Iris includes a reimplementation of [**Vibecop**](https://github.com/bnaylor/vibecop), an independent, paranoid AI guardian (using an auxiliary local model) that, when enabled, evaluates every terminal command or file operation proposed by the primary agent that the "Always allow" rules do not already permit.

*   **Off by default**: Vibecop is a pre-screen, not an approver. With it off (Settings → Vibecop, or the Setup Wizard), nothing pre-screens a call, so every gated command and file operation the allowlist does not already permit asks you — including those of subagents and of the independent goal grader — and so does every gate script `schedule_job` proposes, which asks you whether Vibecop is on or off (#687). An event card for a blocked job run shows no verdict, only the **Approve and run** button. One exception for the grader, and it holds whether Vibecop is on or off: a `run_command` that is exactly an executable check you approved when you locked the goal contract (surrounding spaces, tabs and line breaks aside; no prefixes or additions), run in the workspace the goal had when you approved it, runs without asking, because you already approved that command there. It still asks if the agent has since moved the conversation to another workspace, if the check was added or changed through `amend_goal_contract` (you never saw it), or if the check contains a line break or another control character that could hide part of it from you. The grader may also read any file, or list any directory, inside that approved workspace without asking — reads only, for a path written inside the workspace that really lands there, so a `..`, a symlink that leads outside, or a path that only reaches the workspace through a symlink from elsewhere asks. Such a read is opened step by step from the workspace itself without following any symlink, so a symlink swapped in after the check cannot redirect it; the cost is that a read through any symlink in the workspace, even one that points back inside, is refused rather than followed. Writes, every other command, and reads outside the workspace ask, and the main agent and subagents get none of this. Approving a check approves what it runs, as it is when the grader runs it: approving `make test` also approves whatever the Makefile says by then, and the agent can edit the Makefile in the meantime. Background job runs are unaffected: Vibecop or not, a gated call they make that no allowlist rule or grant covers is refused on the spot and lands on the event card.
*   **Auto-Approval, reads only on your Mac**: If Vibecop judges a call routine and safe, it runs without asking, saving you from prompt fatigue. On your Mac (not in the sandbox VM) that holds only for a call that can only read: a file read, or a command a fixed, conservative check recognises as read-only. That means one of a few programs (`ls`, `cat`, `head`, `tail`, `wc`, `grep`, `rg`, `find`, `file`, `stat`, `du`, `df`, `date` with only `-u`, `-R` and a quoted `+FORMAT`, and the like), with only options on that program's short list of read-only ones, `find` with tests only, and no redirection, pipe, chaining, substitution, glob or variable. Git reads (`status`, `diff`, `log`, `show`, `blame`, `rev-parse`, `ls-files`, listing `branch`, `describe`, `shortlog`, with listed options) run without asking only in a repository no sandbox can reach: its git folder, and every folder from where the command runs up to the repository, outside every folder a sandbox can write. A repository's config can make even `git status` run a program, so in a sandbox workspace's own repository, one nested in a sandbox folder, or one the sandbox made, git asks. The read runs on exactly the repository Iris checked, never one git would otherwise discover. Such a read runs exactly as checked plus a fixed neutraliser Iris adds, shown in its result: no shell, attributes taken from the empty tree, and every config key that can run a program (fsmonitor, external diff, textconv and filters, signature checks, the pager) overridden, so your own pager and diff tool don't apply to it. Nor does your global or system git config (`~/.gitconfig`, `/etc/gitconfig` and Homebrew's), so their settings (`diff.algorithm`, `core.quotePath`, colours, `safe.directory`) don't either: output can differ from your Terminal's, and a repository owned by another user errors rather than runs. It needs git 2.40 or later; an older git asks (#607). A read that runs without asking runs exactly as checked: without your shell's startup files (`zsh -f`), with only the system's `PATH` entries (none that is relative, inside your home folder, inside the working directory, or inside any folder a sandbox can write or ever could, kept in Iris's Keychain item so a deleted conversation's workspace or a removed grant still counts (#616), and a host command can't delete or rewrite it (#717); `config/sandbox-writable-roots.jsonl` is a readable copy, and if it's changed outside Iris, Iris says so once and rewrites it), and with almost none of Iris's environment. If Iris can't read that record, no such read runs without asking until it can, and Iris says so once. So a program found only in `~/bin` or a project's `node_modules/.bin` asks, and so does any read run from your home folder itself or above it. Anything you approve yourself runs as it always has, with your own shell setup. Every other host command, and every file write, asks you whatever Vibecop says; it can still refuse one outright. A turn an MCP guest's message started or steered gets no Vibecop approval at all, on the host or in the VM: it asks you, and Vibecop can still refuse (#1151). In the sandbox VM, Vibecop approves routine work as before, except in a conversation where you let the sandbox write your home folder or another guarded folder ([Subagent Sandboxing](features.md#subagent-sandboxing)): there the VM is no safe box, so only the same read-only commands run without asking. Once you click **Deny** on a command in a conversation, nothing there runs without asking again until Iris restarts, from Vibecop or the read-only check; your "Always allow" rules still apply, since you set them (#600). Whatever let a call run without asking is said under its pill, and in a copied or exported transcript: Vibecop's reason, the rule that matched (global, this project's, or Iris's own folder), the job run's sandbox grant, a check you approved for the goal, YOLO mode (`/yolo on`), auto-approve in a headless run, or "no approval needed" for a tool that has no approval step. A call you approved yourself adds nothing, since your answer is its record (#599).
*   **Guardian Mode**: You can run `/vibecop init` in any workspace (or choose **Vibecop: Generate Rules…** from a workspace-bound conversation's right-click menu, which runs the same thing, #1278) so the primary agent analyzes your project and generates a custom `.iris/vibecop.md` file (writing it asks you, and its rules take effect once you review and trust them: see the next bullet). You can also run `/vibecop tweak <guidance>` to append a rule directly from the composer (#1017): in a conversation with a bound workspace it appends to `.iris/vibecop.md` and trusts the write immediately (unless `.iris/vibecop.md` already has unreviewed rules), and in a conversation without a workspace it is that conversation's own guidance (#1005): stored with the conversation, appended after the global and workspace rules, 4 KB at most, and used only for that conversation (a subagent or job run does not inherit it, and a guest-origin turn is not given it). It only adds allowances: the built-in rules and the host read-only gate still decide what an approval may run, and no tool or model turn can set it. `/vibecop tweak here <guidance>` writes it even with a workspace bound, `/vibecop tweak global <guidance>` appends to `~/.iris/config/vibecop.md` (`~/.iris-dev/config/vibecop.md` in dev builds), which applies across all sessions, and `/vibecop clear` removes the conversation's own guidance. `/vibecop show` displays the active guidance. A conversation started on an [agent profile](agent_profiles.md) whose file has a `vibecop:` field also gets that text, after the workspace rules and before the conversation's own guidance (#1005), under the same limits: it is not inherited by a subagent, not given to a guest-origin turn, and dropped while the profile file is missing or broken.
*   **Refine from what you approved** (#1278): `/vibecop refine` (or **Vibecop: Refine Rules…** on the same right-click menu) reads the last 200 host commands in every conversation bound to the same workspace and proposes one appended line per exact command that you approved yourself at least twice and that was never denied or left unapproved there: `- Routine here, approved exactly as written: `swift test --parallel` (approved 14×)`. It never widens to a program or a prefix (approving `rm -rf build` says nothing about other `rm` commands), and it skips a command with a line break, a backtick, or more than 200 characters rather than copy it into the rules. No model is asked. A conversation a job ran, a guest's session, and any conversation a guest's, a peer's or an unattended message reached don't count, and neither do calls that YOLO, auto-approve, an allowlist rule or Vibecop itself approved. It only adds allowances (never an "always escalate" line), keeps every existing line exactly as it is, and shows the proposal first; the write then asks you like any write to the workspace's `.iris/`, and once you approve it the file is trusted as Iris's own write. It refuses while the file has unreviewed rules.
*   **The workspace's `.iris/` is yours to change, not the agent's** (#617): `.iris/vibecop.md`, the project allowlist (`.iris/permissions.json`) and the sandbox setting (`.iris/sandbox.json`) decide what later runs without asking, so a model or tool write into a workspace `.iris/` always asks you, even when Vibecop approves it or an "Always allow" rule covers it, and an unattended run's is refused. So `/vibecop init` costs one approval, then a review: the rules it wrote take effect once you trust them (below). Iris's own writes there (an "Always allow in project" click, a sandbox setting you change) do not ask again. In the sandbox VM, `.iris/` is mounted read-only over the read-write workspace, created empty first if it is missing, so nothing in the VM can write, rename, remove or link over it; a workspace whose `.iris` is a symbolic link or not a folder refuses sandboxed commands until you fix it. Iris reads these files only as plain files with one link, so a symlink or hard link to a file elsewhere in the repository (which the VM could write) is ignored. And Iris uses these files only as it wrote them, or as you trusted them (#625): a file that came with the folder (a cloned repository's own `permissions.json`, say), was edited outside Iris, was written by the agent (even with your approval, which shows the path, not the rules), or was planted in a nested `.iris/` the sandbox could write, is treated as absent. Its rules are off, the sandbox setting is the default, and Vibecop gets no workspace rules. Linking such a workspace says so in the conversation; to turn them on, right-click the conversation and choose **Review Workspace Rules…**, read the files, and click **Trust These Rules**. Iris keeps a fingerprint of each trusted file in its own settings folder (`config/workspace-trust.json` under `~/.iris`), which nothing the agent does unasked can write. **After upgrading**, every workspace's existing `.iris/` rules are untrusted until you review them once, so a project allowlist you rely on stops applying until you do. On your Mac a command is caught when it names a workspace `.iris` (best effort: a script or glob can reach a path it does not spell), which is why the VM side is a mount.
*   **A garbled verdict is asked once more** (#914): a local model sometimes returns a verdict word that is not one of `APPROVE`, `ESCALATE` or `DENY` ("APPRORE"), about 1 reply in 20 on gemma4:12b. Iris sends an Ollama model the verdict's real JSON schema, and asks again once when the reply is still not one of the three exact words; a second one asks you. Only an exact `APPROVE` ever approves: nothing is matched loosely, and a real `ESCALATE` or `DENY` is never asked again.
*   **Escalation**: If the command is destructive, touches restricted paths, or isn't listed in the Guardian config, Vibecop blocks it and escalates to a user confirmation dialog.
*   **Model Flexibility**: Vibecop supports multiple backends — embedded `llama.cpp`, `MLX` for Apple Silicon, cloud providers, and local **Ollama** daemons. When Ollama is selected, Iris auto-probes the daemon to discover installed models, offers a model picker, and can pull the recommended `gemma4:12b` directly from the UI. A clear warning banner is shown if the Ollama daemon is not reachable. With **Cloud**, Vibecop runs on your primary provider: on the model you set in Settings → Vibecop → Cloud Model, or, left empty (the default), on your easy tier's model, which Settings shows as the effective model. Settings warns when the name does not look like your primary provider's, and a model the provider does not have falls back to the easy tier for that check, with one notice the first time (#620). Tier 3's Cloud engine reads the same Cloud Model, whichever engine Vibecop uses ([guard design](prompt_injection_guard_design.md#tier-3-auxiliary-model-classifier-probe-implemented), #800).

## Always allow, and the path a file operation is judged by

Includes "Always allow" and "Always allow in project" persistence. Neither button is offered when
the rule text Always Allow would actually save — the generalized prefix for most commands (#1102),
the whole call for one that never generalizes — looks like it contains a credential (a bearer
token, a provider API key, a named `token=`/`password=`-style argument, or another secret-shaped
substring): a saved rule would write it to `permissions.json` in plaintext. The dialog says so, and
the current call still runs as
approved; only the standing rule is refused (#1140). A file operation is asked about, checked against those rules and run by the path it will actually touch: `~` expanded, a relative path joined onto the conversation's workspace (or the app's own directory when there is none), and `..` and symlinks resolved, so a link in the workspace that points elsewhere is shown at its target, and a rule saved in another spelling of the same file still matches. The file is then opened one directory at a time without following any symlink, so if a link has been swapped into that path by the time the tool runs (or by the time you click **Approve and run** on a card), the call is refused rather than followed. For the same reason a write to a dangling symlink is refused, not turned into a file. A path containing a NUL character is refused outright. One consequence for existing rules: an "Always allow" rule saved for a *relative* path no longer matches, because a relative path names no file until it is resolved, so you will be asked once more for those and the new rule is saved as the full path. A project rule's relative path is still read relative to that project.

### Always allow on a command saves what it does, not its exact text (#1102)

A command rule used to be the whole command, byte for byte, so it almost never matched again. Now Always Allow on a command saves a *prefix* for each part of it: the program, plus the subcommand for tools that have them. `cd /tmp && git -C foo status --short | head` saves `git status`, and `swift test --filter X 2>&1 | tail -40` saves `swift test`. The dialog shows the rule before you click, and (#1137) lets you edit it: add the next words of the command to narrow it (`swift test` becomes `swift test --filter`), reset it to what was proposed, or tick **Exact command only** to save the whole command. An edit can only narrow: it must start with the proposed prefix, be words the command actually has, in order, in plain words (letters, digits and `_ . / : @ + -`, single spaces, no quotes, `=`, shell characters or hidden characters), and a rule that would hold a credential-shaped word is refused like the proposed one. A one-word rule (a read-only program such as `ls` or `cat`) is not narrowed, since its read-only and workspace re-check applies only to a one-word prefix. The same check runs again when the click is resolved; a rule it refuses saves nothing (the call is still approved once, with a note in the conversation), never the broader proposed rule in its place. A later command matches when every part of it starts with a saved prefix and its other words are plain arguments. Parts that need no rule can ride along: `cd` to a path, `pwd`, `true`, `echo`, a filter after a pipe that reads only its input (`head`, `tail`, `wc`, `sort`, `uniq`, `cut`, a `grep` with only a pattern), and `2>&1` or `>/dev/null`. A command made only of ride-alongs is never approved by a rule.

It is deliberately narrow. These commands get no prefix, and Always Allow saves the exact command as before:
- anything with shell features the check doesn't model: substitution, redirection to a file, subshells, globs, variables, background `&`
- programs where any arguments can mean any code, any destination or any destruction: shells and interpreters, `env`, `xargs`, `sudo`, `find`, `make`, `curl`, `ssh`, `rm`, `mv`, `cp`, `sed`, `awk`, and others
- a subcommand off its tool's short list (`git push`, `git config`, `npm install`, `gh api`)
- git with any global option other than `-C` and `--no-pager`, or an argument that runs a program or writes a file (`--upload-pack`, `--output`, `--ext-diff`)
- a program spelled with a path (`/`)

A tool Iris doesn't know keeps its verb only when that verb is on a short read-only list (`status`, `list`, `ls`, `show`, `get`, `describe`, `version`, `info`, `inspect`, `logs`, `help`), never just its name or an arbitrary verb. A bare-program prefix (`cat`, `ls`, `rg`, …) re-checks `ReadOnlyCommand`'s flag allowlist when matching and confines file-reading paths to the conversation's workspace (paths outside it, such as `~/.ssh` or `/etc`, still prompt). Prefix rules apply only in attended chats, and `cd` or `git -C` must stay inside the conversation's workspace. An unattended job run never uses them, only its grant and exact rules. A turn an MCP guest's message started or steered (or a session it delegated to) uses no saved rule at all, exact or prefix: it asks you (#1141). Rules saved before this change keep matching exactly as before.
