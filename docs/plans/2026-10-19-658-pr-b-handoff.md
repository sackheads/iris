# Handoff: #658 part B, retire the old sandbox git guard

For the agent taking this over. It assumes no context beyond this repo and its `AGENTS.md`.

## Background in one paragraph

When a sandboxed (VM) workspace is a git repository, the VM must not be able to choose what git on the person's Mac runs. Hooks, and config keys like `core.fsmonitor` or filter drivers, can run programs. The first fix (#623, #632, #651) was a guard, `GitConfigGuard`. It watched the host repository's config, put back disallowed changes, and overrode risky keys for Iris's own host git. Each round of review found another bypass. #658 replaces that approach.

**Part A (PR #662, approved, about to merge)** gives the VM its own copy of the repository's git dir. The copy lives under `<iris home>/sandbox-git/` and is mounted where the VM's git looks. The person's `.git` is mounted read-only, and commits come back to the host as a bundle. So the VM can no longer write the host's git dir at all, and most of `GitConfigGuard` is now dead code.

**Part B (this handoff)** removes the dead code and keeps the small part still needed.

## What part B must do

### Keep

1. **The pointer checks from part A.** These are `SandboxGit.pointerProblems`, `quarantinePointers` and `checkHostPointers`, plus the `.gitmodules`/`.lfsconfig` notices. They stay as they are.
2. **The list of folders a sandbox has mounted read-write,** persisted across restarts. Today that's `GitConfigGuard`'s store, `config/sandbox-workspaces.json`.
   - Reduce each entry to the folder path. Old files must still decode: ignore the extra fields, and follow `AGENTS.md` invariant 1.
   - Keep #641's handling of an unreadable store. The file is moved aside to `.corrupt` (never overwriting an existing copy), and a store that can't be moved aside is never written over.
3. **Untrusted-repository judging,** for repositories the VM may have made. This is the ruled behaviour:
   - **Trigger.** Before each host `run_command`, walk up from its working directory to the nearest `.git`, without running git. Do the same for each `git -C <path>` in the command, resolved against the working directory.
   - **Scope.** Judge only a repository that sits inside a folder in the mounted list.
   - **Trusted.** A repository is trusted if its canonical common dir has a sandbox-git copy whose recorded common dir matches. The marker file `iris-sandbox-seed` in each copy holds the canonical common-dir path on its first line, so check it rather than trusting the hash. Everything else found by the walk is untrusted. That includes a repository the VM created with `git init` at the root or in any subfolder, and the person's own nested clones inside a mounted folder, since their `.git` is in the VM-writable worktree.
   - **Judging.** For an untrusted repository:
     - If any of its config files (`config`, `config.worktree`, and each `modules/**/config`) sets a key outside the allow-list, refuse the host command with a message naming the key. The allow-list is `GitConfigFile.isAllowed` plus `GitConfigGuard.initDefaults`, as today's `untrustedRisk` does.
     - Carry over #651's git-lfs exemption: `WorkspaceGit.lfsValues`, matched on the **exact value**, never the key name. An LFS repository is then not refused, but `filter.lfs.clean = <anything else>` still is.
     - Otherwise run the command with no hooks: set `GIT_CONFIG_COUNT=1`, `GIT_CONFIG_KEY_0=core.hooksPath`, `GIT_CONFIG_VALUE_0=/dev/null`, after removing any inherited `GIT_CONFIG_*`.
   - **Notice.** Post a notice once, the first time Iris sees each untrusted `.git`, naming its path. The docs must say that git from the person's own terminal inside such a repository is not protected.
   - **Unreadable store.** While a `.corrupt` copy exists, run the judging on **every** repository the walk finds, mounted or not, again with the LFS exemption and with trusted copies exempt. Say so once per launch, including that deleting the `.corrupt` file ends it.

## Tests required (Swift Testing, `Tests/irisTests/`)

Rewrite `WorkspaceGitTests.swift`'s guard suites. Keep `GitFixture` and the parser tests, and drop the revert and override tests. New tests:

1. A root `git init` in a mounted folder with a risky key: the host command is refused, with the key named. Without a risky key, it runs with no hooks: a marker hook in that repository must not fire. The notice is said once.
2. The same for a nested repository inside a mounted repository that has a sandbox copy.
3. A walk from a subfolder of the nested repository finds it.
4. `git -C <path>` from a working directory outside the mounted folder is judged.
5. LFS: git-lfs's exact values are not refused; a modified `filter.lfs.clean` is.
6. A repository outside every mounted folder is untouched (ordinary).
7. A copy whose marker names a different common dir does not make the repository trusted.
8. An unreadable store: repositories outside mounted folders are judged too. Deleting `.corrupt` ends it at the next launch, meaning a new `GitConfigGuard(store:)`.
9. Keep #641's store tests, adapted: a bad entry among good ones, a truncated file, a newer format with extra fields, the next save keeping `.corrupt`, and can't-move-aside or can't-copy-aside never writing over.
10. End to end through `ToolExecutor.runCommand` on the host: a hook in an untrusted repository doesn't run, and a refused command doesn't run.

Mutation-check each fix: break it, see a test fail, restore it. **Commit before mutating.** A `git checkout -- Sources` used to restore a mutation will also wipe uncommitted edits. That happened during part A.
