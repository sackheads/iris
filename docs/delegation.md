# Graded delegation

Moved from the feature tour ([docs/features.md](features.md)), word for word (#534).

When the main agent delegates a unit of work, it can hand the subagent a scoped definition-of-done. The finished run is graded by an independent evaluator in a fresh context that never saw the subagent's transcript, so the result carries a trusted verdict ("2/3 met", per-criterion) beside the subagent's own unverified summary — the two are always labeled and never conflated. A grade still running when its work is stopped — the run it belongs to closes, or you stop the conversation that delegated it — is stopped too, its model call cancelled, and comes back as "grading stopped", never as a verdict; a goal whose own final grade is stopped that way is not marked complete. Delegation without criteria behaves exactly as before: no contract, no grade. Either way the subagent works in a goal loop of its own: a turn that ends without `goal_complete` is followed by a reprompt, up to its iteration cap (10 by default, Settings → Agent Limits → Max subagent iterations, separate from the main agent's), and a subagent that reaches the cap without `goal_complete` comes back `failed`, with no summary turn. Each reprompt is a full model round over the subagent's history so far, so a subagent that keeps going costs up to the cap's worth of rounds, each charged to whoever delegated it (in a job run, to the run's budget, which can stop it sooner). Each turn has its own time limit, restarted every turn (15 minutes by default, Settings → Agent Limits → Subagent turn timeout): a turn that runs past it is cancelled and the subagent comes back `timed out`. The pause between turns does not count, and neither does time the Mac spends asleep (#624); time a turn spends waiting on your approval does. There is no separate limit on the whole subagent; the iteration cap times the turn limit bounds it, and in a job run the run's own deadline stops it sooner.

## Subagents on other providers

`invoke_subagent` can run a subagent on another provider and model than the conversation's: an independent view from another model family, such as a security review on DeepSeek. The providers are the ones switched on in **Settings → Models → Subagent providers** ([features](features.md#subagent-providers)).

- **Declaring the arguments:** `provider` and `model` are declared only while a provider besides the primary is usable. With none, the tool looks exactly as before.
- **Resolved before anything starts:** an unknown provider, a family that's switched off or has no key, an address changed since its key was entered, or a model id that isn't on the provider's list is refused with a sentence naming what's configured. Nothing falls back to the conversation's own model: a review that quietly ran on the parent's model would carry the right label on the wrong review.
- **Inside a job:** a subagent on another model family is charged to the run at that model's own price, converted to the run's weighted tokens through dollars (#239). The rates are LiteLLM's public price list, which the app fetches at most daily into a protected file under `config/`. If there's no fetch, the bundled snapshot is used. A fetched rate more than 10x off the snapshot's is rejected. A model with no known rate is charged its family's highest rate. A custom endpoint with no known family is charged the highest rate of any family. Either way the card marks the figure "estimated" and says how to set a rate. A server on this Mac (localhost) costs nothing, but its tokens still count at the primary's weights, so a job's budget still bounds it.
- **Where it ran:** the subagent's result names the provider and model it actually ran on.
- **Grading:** a subagent's grader (when you give `criteria`) stays on the conversation's own model, so the work is judged by the parent's model, never by itself.
- **Approvals:** an approval a routed subagent asks for names its provider and model. One on a custom endpoint offers **Allow Once** only, never Always Allow.
- **The guards don't change.** Vibecop and the prompt-injection guard (P1 to P3) judge a subagent's calls and tool output exactly as before, whatever model it runs on. Vibecop's cloud engine stays on the primary provider.
