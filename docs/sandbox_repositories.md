# Repositories in the Sandbox

Git on your Mac runs programs a repository names, in its hooks and in its config (`core.hooksPath`, `core.fsmonitor`, `diff.external`, filter drivers). So when a sandboxed workspace is a git repository, Iris keeps the VM from choosing what your next `git commit` runs (#623):

- In the VM, the repository's `.git` is a mount of its own, so it can't be renamed or replaced, and `.git/hooks` is read-only (created first if it is missing). Commits, branches and checkouts in the VM still work. A `.git` or `hooks` that is a symbolic link refuses sandboxed commands.
- Before and after every sandboxed command, and before every host one, Iris compares the repository's config files (with those of submodules already there, and a worktree's `.git` file) with the copy it kept. The VM may add or change remotes, upstream branches and `user.*`. Any other change, including `include.path`, a submodule's or Git LFS's settings, or an `ext::` URL, is put back byte for byte, and the reply says so. This includes a change you make yourself while the sandbox session is open. A file Iris could not read when it started watching (too large, not a plain file) is never written over; the reply only says it changed. When Iris cannot put a change back, a host command run in that repository, or naming it, is refused until a check finds it clean. The refusal survives the sandbox session ending and an Iris restart: after a restart Iris re-tests only what it was refused for, and takes a fresh copy to compare against once that is fixed.
- The VM can't add a submodule to the repository, or repoint one it has. Iris reads the index itself (no git run on your Mac) before and after every command; a submodule entry that is new, or whose `.git` changed, has that `.git` renamed to `.git.iris-quarantine` beside it, and a module repository new under `.git/modules` likewise, so neither `git status` nor a later `git submodule update` uses what the VM wrote. Nothing is deleted, and the reply says what moved: if you trust it, rename it back once the sandbox session has ended. An index Iris cannot read refuses host commands in that repository until it can. A plain repository cloned into a subfolder, with no entry in the index, is left alone.
- A repository the VM creates in a mounted folder that had none is never trusted: Iris keeps no copy of its config to restore, but judges it as it stands, and a key that can run a program there refuses host commands in that folder until it is removed. Any submodule in it is the VM's, and is moved aside like one added to your own repository. Host git runs no hooks in it. Iris remembers the folders a sandbox has mounted, and which had a repository first, across restarts (`config/sandbox-workspaces.json` in its settings folder).
- A host `run_command` in a conversation with a sandbox session, in a folder a sandbox has mounted (or a linked worktree of its repository), or naming one of those folders, runs git with the fixed-name keys that start programs overridden. Your own global and system values for those keys still apply. Git started this way never opens an editor (`core.editor` is `true`), and runs only the repository's read-only `.git/hooks`. A `core.hooksPath` that points into the worktree, such as husky's `.husky`, is not run.

What this does not cover: a change the VM made that is still in place when Iris restarts, which becomes what later checks compare against, since Iris keeps no copy of a repository's files across a restart (#639). Git run from your own terminal while a bad write is in place. A write made during a command is put back when it ends, but a background job left running in the session container can write after that check, and its write stays until the next command or until the idle container is removed (a folder watch to close this is #633). Iris's own host git is covered then for the fixed-name keys, but not for keys with a name of the repository's choosing (`filter.<x>.clean`, `diff.<x>.textconv`, `merge.<x>.driver`, `remote.<x>.uploadpack`, `submodule.<x>.update`, `difftool.<x>.cmd`, `mergetool.<x>.cmd`, `tar.<format>.command`) or for `alias.*`, which runs a shell command when you use that alias. Nor does it cover a repository in a subfolder of the workspace that is not a submodule (made by `git init` or a clone there): git run in that folder reads its config, though git run in the workspace does not. Nor `git send-email`'s program settings (`sendemail.*`), or a host command that sets `GIT_CONFIG_COUNT` itself. The config and hooks of submodules that were already there are covered like the repository's own.
