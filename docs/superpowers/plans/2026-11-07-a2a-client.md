# Iris A2A Gateway Client Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give Iris an A2A client that talks to the homelab gateway over HTTPS (JSON-RPC + SSE) — outbound (Iris calls remote agents) and inbound (Iris receives tasks, runs them in an isolated, confined session, streams results back). (Iris no longer self-describes as "guest-tier": it verifies peers and signs its own traffic; inbound peer tasks are *confined* via the `a2a-remote` lane, and Iris's own mesh enrollment tier is a romar/config fact, not a property of this client.)

**Architecture:** Iris **verifies every inbound peer frame itself — both delivered tasks AND the responses to its own outbound calls (`status-update`/`artifact-update` events) — and signs its own outbound.** The same relay carries both directions, so an unverified outbound *response* is forgeable exactly like an unverified inbound *task*; verification is not a Milestone-B-only concern. The committed contract is romar#396 (`peer-signature-spec.md` v2, "sign exact bytes, verify-before-parse"), and the identity model is #974 H4. The gateway is a **relay, not an identity authority**: Iris does not trust a relayed `authority.tier`, it derives tier/identity from its own local key/grant registry once the signature verifies. (This supersedes the earlier "guest-tier, no client crypto, trust the gateway" design — see the 2026-11-09 H4 decision.) Outbound reuses the existing `URLSession` + bearer-token pattern and the `LLMStream.swift` SSE stack. Inbound is a persistent SSE "inbox" connection with an application heartbeat and a two-phase delivery ack; delivered tasks run in an isolated `lane: "a2a-remote"` session under a new `Principal.a2aRemote` gated by a three-tier path/tool policy, **after** the signature verifies. Built in two milestones, **both gated on the #974 crypto core** — keypair generation + Keychain storage, the signer, the verifier, enrollment, and the replay seen-set are **owned by #974 H4, which needs its own implementation plan before either milestone can start** (today #974 is still an open *design* PR, #999, with no build plan). **A (outbound)** is the lighter half but is **not** "testable against the live gateway immediately": Iris's public key must first be enrolled with the peers (an out-of-band human step), and every peer response it receives must verify. **B (inbound)** is the heavier, security-critical half.

**Tech Stack:** Swift / `IrisKit`, `URLSession.bytes` streaming, `DispatchSourceTimer`, GRDB (artifact ledger), SwiftUI (Settings). Tests: Swift Testing + `MockURLProtocol`.

**Spec:** `~/iris-client-spec.md` (rev 2) — kept **out of the repo** because it carries homelab infra specifics (real hostnames, KV/endpoint names, the Keychain service string). This plan abstracts those: the gateway base URL, bearer token, and service names are read from config/Keychain, never hard-coded here. Implementers read the spec for the exact wire shapes; this plan maps them onto iris.

## Global Constraints

- **Client-side crypto is REQUIRED (bidirectional), per romar#396 + #974 H4.** IrisKit implements Ed25519 **verification** on every inbound frame — delivered tasks *and* received responses — and **signing** on every outbound task/reply. Verify-before-parse; resolve the signing key within the sender principal's own registered keyset; bind the recipient **by direction** (romar §5.1): `.in` kinds (`message`/`cancel`) addressed to `iris`, while `.events` responses are bound to the outstanding request they answer (`events_request_mismatch`), enforced inside the verifier; derive tier/identity from Iris's **local** registry, never the relayed `authority.tier`; **fail closed** — a missing/invalid/unverifiable signature is hard-rejected and **never coerced to `guest`**, and relay-attested traffic is rejected unless the user opted into an explicit "gateway" profile. The byte-exact wire format stays **out of this repo** — read it in romar#396; this plan references it. (This replaces the former "zero client crypto, trust the gateway" constraint.)
- **The full per-frame MUST list is romar §5.1 — take it verbatim, do not re-derive.** Beyond the above, that list requires: **present `envelopeId`** (bounded minimum length, the replay nonce) and **strict RFC 3339 UTC `ts` (always) and `deadline` (required on the `message` kind only; other kinds bounded by `ts + 24h`)** — "strict" means a regex, not `ISO8601DateFormatter`/`fromisoformat` defaults, which accept non-RFC-3339 forms; **`kind` ↔ channel binding** (a frame's `kind` must match the channel it arrived on — so a signed event cannot be replayed as a task or vice versa; the allowed-kinds-per-channel table is **pinned in romar §5.1** — map it, do not invent one); **reject duplicate JSON object keys** on the raw bytes before decoding (the #974 H4 **core** owns the scan over the signed bytes `B`, `StrictJSON`; the **outer-frame** scan is Task 1's, which may call the same helper; note: whether Swift's `JSONSerialization`/`JSONDecoder` silently keep last-wins is **unverified**; the explicit scan is required regardless, and the macOS behaviour recheck #999 H4 lists must cover duplicate-key handling, not only the outer frame); and **accept only the new signed format from day one — no downgrade path** (a downgrade is just the relay choosing the weaker check).
- **Replay + enrollment.** The replay nonce goes in a persisted, per-peer-bounded seen-set written **before** execute; a per-task deadline — **required on the `message` kind only**, capped at **`deadline ≤ ts + 24h`**; other kinds are bounded by `ts + 24h` — bounds lifetime (romar §6) — this is the replay/seen-set bound, distinct from any local execution timeout; no fixed `abs(now−ts)` window (a queued task must survive the laptop sleeping). A duplicate is **rejected *and* acked** (never nacked, or the relay redelivers forever). Peer public keys are enrolled **out of band** in Iris's per-profile registry at the human-approved first grant; the gateway's key distribution is not Iris's trust source. The key registry, seen-set and signing primitives are owned by **#974 H4** and consumed here.
- **Every deterministic reject is consume-and-drop; two faults are retryable-with-a-bound, and one caller bug is neither (#1036 security review).** `PeerSignatureVerifier.verifyAndAdmit` throws two shapes of error, and #931 must handle both, not just the first: a `PeerVerificationError(reason: PeerRejectReason)` for a decided frame, and a handful of raw error types the verifier deliberately does **not** wrap, because romar names no `PeerRejectReason` for them. Every `PeerRejectReason` case names a specific frame that is bad and will be bad again on redelivery — `invalidSignature`, `unknownKey`, `tsInvalid`, `deadlineExpired`, `principalMismatch`, `duplicateKey`, the rest — so every one is **consume-and-drop**, never requeued, in `A2AChannel`'s own inbox/events terms, not a transport verb. The four raw, unwrapped `StrictJSONError` cases that fire after the signature check (`.malformed`, `.invalidEncoding`, `.tooDeep`) and an unmapped `FrameDecodeError` are decided the same way — also consume-and-drop — even though #931 catches them as their own Swift error type rather than a `PeerRejectReason`. Two cases are different in kind, not degree: `PeerRejectReason.seenSetUnavailable` and the raw `RegistryError.unavailable` (thrown *before* the signature check, when the key registry file itself cannot be read) both mean the frame's own validity was never decided, so #931 should **retry with a bound (backoff, capped attempts or time), not drop and not retry forever** — `RegistryError.unavailable` can be a damaged file a human has to fix, so an unbounded retry redelivers that frame forever, exactly the loop this item exists to prevent, just shaped as a stuck retry instead of a stuck drop. `PeerRejectReason.seenSetFull` is neither: it is a legitimate peer that has outrun its bound, not a fault and not evidence the frame is bad — #931 should retry with backoff until the ledger's prune frees room, or drop, but either way it is its own named case, not folded into either bucket silently. `VerifierUsageError` is none of the above: it is a raw, unwrapped type that fires *before* any check on the frame (a caller contract bug in #931's own call — e.g. channel/outstanding mismatched), not "a frame that already passed verification," so dropping or requeuing it both treat a bug in #931's own call as if it were something the peer sent. Surface it loudly (log, alert) as an implementation defect, never as a per-frame outcome.
- **Conformance vectors are the one wire artifact that DOES live in the repo.** The "no wire format in this repo" rule covers homelab infra specifics and the byte-exact contract prose; it does **not** cover romar's shared conformance/negative test vectors, which are vendored into `Tests/` by design (byte-exact fixtures, by commit or CI fetch). Do not "fix" the repo by dropping them.
- **No infra specifics in code or this repo.** Gateway base URL = a guarded config setting; bearer token = a Keychain secret; no literal hostnames, KV names, or the Keychain service string in source comments or docs committed to the repo.
- **Invariant 4:** every timer/heartbeat/deadline uses a `DispatchSourceTimer` or `UptimeClock`, never `Task.sleep` on the cooperative pool.
- **Invariant 1:** every new persisted `Codable` field uses `decodeIfPresent` or a `CodingKeys` exclusion.
- **Invariant 6:** no new tool is broadcast on plain turns; inbound-only capabilities are gated by the new principal, not declared globally.
- **Deny-first precedence (security invariant):** hard-blocked dirs + secret deny-globs always win over any auto-allowed or user-added directory. A user-added allow dir can never un-block a secret inside it.
- **Tests author no new attack payloads.** Injection/abuse tests reuse existing dataset rows, framed as a2a inbound.
- **Guard the default-timeout trap:** a persistent inbound stream must use a dedicated `URLSessionConfiguration` with a large/disabled `timeoutIntervalForRequest`; the LLM clients' `LLMRequestPolicy.timeoutSeconds = 180` would kill an idle inbox stream.

## Review Focus

- **Sleep/wake mid-task (the core scenario).** Lid closes after a `task-delivery` frame but before the 5s ack → the task must deterministically fail (`IrisDeliveryAckTimeout`) and NOT execute on wake; an already-acked task must survive an SSE blip (heartbeat alive) and recover across an app restart. Owned by Task 4; tests there.
- **A compromised/hostile peer task escalating.** The three-tier policy must hard-block secrets/`~/.ssh`/`~/.iris` even inside an auto-allowed dir, and must not let an inbound task self-approve a write/send. Owned by Task 5; test deny-glob-wins and the no-self-approve path.
- **Injection in content the task fetches** (a hostile email body retrieved by an inbound task) hijacking the `a2a-remote` turn. The guard must run on *fetched* untrusted content (external/tool-output source), not only on the task text. Owned by Task 5/6; test with an existing injection row delivered as a fetched doc.
- **The 180s idle-stream timeout** silently dropping the inbox connection. Owned by Task 4; test that the inbox session config does not carry the 180s interval.
- **File size caps, SHA mismatch, and out-of-order chunk reassembly.** >128 KiB inline rejected; object SHA verified on read; inbound `MEDIA` artifact chunks reassembled by `artifactId` in order. Owned by Task 3 (outbound) and Task 6 (inbound reassembly).

# Milestone B — Inbound (heavy, security-critical)

## Task 4: Persistent inbound SSE inbox loop (connection, heartbeat, ack, reconnect, lifecycle)

> **Delivery follows romar's replay rules (§6), not just a two-phase ack.** The `envelopeId` is written to the
> persisted seen-set **before** the task is handed to Task 6 (write-before-execute). A **duplicate is rejected
> *and* acked** — never nacked, or the relay redelivers forever — and every rejected frame is acked after its
> rejection status posts. This is **at-most-once** delivery by design: a crash between the seen-set write and
> execution drops that task; say so, don't pretend otherwise. The seen-set itself is not a follow-up (only
> in-flight-state recovery across restart is). The seen-set is #974 H4's, consumed here.
>
> **Not every rejection drops the same way (Global Constraints, "Every deterministic reject is
> consume-and-drop...").** A true duplicate, every deterministic `PeerRejectReason`, and the raw
> post-verification `StrictJSONError`/`FrameDecodeError` cases are all consumed-and-dropped — acked,
> never requeued, because redelivering a bad frame changes nothing. `PeerRejectReason
> .seenSetUnavailable` and the raw `RegistryError.unavailable` are different: the frame's validity
> was never decided, so #931 retries with a bound (backoff, capped attempts or time) rather than
> dropping or retrying forever. `PeerRejectReason.seenSetFull` is its own case: a legitimate peer
> over its bound, not a fault — retry with backoff until `prune` frees room, or drop; either way,
> name it, don't fold it into the other two silently. `VerifierUsageError` reaching here is a raw,
> unwrapped bug in #931's own call into the verifier, not a frame outcome — it is surfaced loudly,
> not acked and not requeued.
