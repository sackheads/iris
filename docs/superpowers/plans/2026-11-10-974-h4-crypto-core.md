# #974 H4 — Peer-Signature Crypto Core Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the shared Ed25519 peer-signature crypto core — Iris's own keypair + Keychain storage, a per-profile peer public-key registry, a signer, a verify-before-parse verifier, and a persisted replay seen-set — the primitive that the A2A client (#931) and, later, the MCP service (#965) consume to verify who sent a frame and to sign Iris's own outbound.

**Architecture:** A self-contained IrisKit component with **no transport and no `Principal` wiring** (those live in #931). It implements the committed romar contract (sign the exact transmitted bytes, verify-before-parse, no canonicalization). Keys resolve from Iris's **own local per-profile registry**, never from the relay; verification is **fail-closed**. The verifier enforces verify-before-parse itself by taking the transport's strict decode as an injected closure over a transport-neutral `VerifiableEnvelope` view, so the security-critical order cannot be reordered by a caller and the core carries no A2A-specific types. Bidirectional: Iris signs its outbound too. The seen-set is GRDB on the existing `ConversationStore` writer; the registry is a protected-dir JSON store the model can never self-write.

**Tech Stack:** Swift / `IrisKit`, CryptoKit `Curve25519.Signing` (Ed25519 — the first asymmetric crypto in the codebase), `KeychainManager` (private seed), GRDB (seen-set, on `ConversationStore`'s shared writer), JSON-under-`config/` (registry). Tests: Swift Testing + romar's **vendored** conformance vector.

**Spec:** `docs/specs/2026-11-09-unified-access-boundary-design.md` (#974 H4) is the Iris-side design. **The byte-exact wire contract lives in romar and is referenced, not copied here** — `projects/active/a2a-gateway/peer-signature-spec.md` (romar#396/#397) for the frame, the domain-separated signing input (§3/§4), the verification order and the field/reason-code MUST list (§5), and replay (§6); `KEY-PROVISIONING.md` (romar#402) for the public-key wire form and enrollment. The implementer reads romar for every exact value; this plan maps that contract onto Iris types, persistence, and tests. **Do not transcribe the romar wire format into this repo.**

## Global Constraints

- **Sign/verify the exact bytes, verify-before-parse, no canonicalization** (romar §3/§4/§5). Resolve key → Ed25519-verify the domain-separated signing input → only then decode the envelope bytes once (strict, duplicate-key-rejecting) → then the post-parse checks. The envelope bytes are never decoded before the signature verifies.
- **Key id = sender principal; resolve strictly within that principal's keyset** (romar §2). An optional `keyId` defaults to the principal and is resolved only among keys registered for that principal — never a flat global map. There is **no gateway-key fallback** and no gateway trust source (romar#403): if a gateway cache is ever added it is a separate store that never writes into the pinned registry.
- **The full post-parse MUST list and the reason-code set are romar §5.1 — take them verbatim from romar, do not re-derive.** They include the sender/recipient bindings (recipient binding splits by direction — `.in` addressed to Iris, `.events` bound to the outstanding request), the kind↔channel binding, the `envelopeId`/`ts`/`deadline` rules, the strict RFC-3339 grammar, derive-tier-from-local-registry-not-self-claimed-authority, fail-closed-never-`guest`, and reject-gateway-attested. This plan references them by name; the exact thresholds, the regex, and the reason-code strings come from romar.
- **Replay** (romar §6): a persisted, **per-peer-bounded** seen-set, **written before execute**; retention matches the acceptance window; a full set **rejects, never evicts**; a corrupt/unreadable store **fails closed and survives restart** (does not auto-recover to empty); a duplicate is rejected **and acked** by the transport. The "interrupted redelivery → terminal status" behaviour (romar#409) is the **transport's** (#931 Task 4), acting on the duplicate signal — out of scope here.
- **Bidirectional.** Iris enrolls its own keypair and signs outbound; its public key is pinned out of band on each peer, so the enrollment surface must display it. **Outbound signing is not relied on for reply integrity toward a peer until romar#403 closes** — the signer is still built; only the reliance is gated.
- **Every rejection logs its romar §5.1 reason code** with the `envelopeId` when present, so a misconfiguration never presents as silent loss.
- **Conformance vectors are vendored from romar**, not hand-copied; the negative vectors drive the reject-code tests. romar's fixture currently omits an `events_request_mismatch` vector — add one locally until it ships. Tests author **no new attack payloads**.
- **Invariant 1** (persisted `Codable` fields `decodeIfPresent`/`CodingKeys`-excluded); **Invariant 4** (timers/deadlines on `DispatchSourceTimer`/`UptimeClock`, never `Task.sleep`); **Invariant 7** (no process-global mutation in tests — inject `IrisPaths(root:)`, a suffixed test `KeychainManager`, and a temp GRDB writer; drive time from an injected `now`, never `Date()` inside the verifier).

## Review Focus

- **A relayed/forged `.events` response answering no outstanding request** (wrong peer, `taskId`, or `correlationId`) — rejected with romar's events-mismatch code, never admitted. A response is forgeable exactly like an inbound task. *(Task 4.)*
- **Cross-principal key confusion** — a valid signature claiming one principal but signed by a key registered under another — rejected as an unknown key (keyId resolves only within the claimed principal's keyset). *(Task 2 + Task 4.)*
- **A queued task delivered after the laptop slept, still inside its deadline** — admitted (no fixed `abs(now − ts)` window); a replay of the same `envelopeId` after wake rejected as a duplicate. *(Task 4 + Task 5.)*
- **A corrupt/unreadable seen-set at startup** — fails closed (rejects every inbound) and does **not** begin empty after a restart. *(Task 5.)*
- **Duplicate JSON object keys** in the frame or the envelope bytes — rejected; a macOS test pins `JSONSerialization`/`JSONDecoder` last-wins behaviour rather than assuming it. *(Task 6; the strict decode that detects it is #931 Task 1's, exercised here through the verifier.)*

## Task 4: Verifier — verify-before-parse + the romar §5.1 MUSTs

**Files:**
- Create: `Sources/IrisKit/A2A/Crypto/PeerSignatureVerifier.swift`
- Test: `Tests/irisTests/PeerSignatureVerifierTests.swift`

**Interfaces:**
- Consumes: `PeerKeyRegistry` (Task 2), a `SeenSetStore` the verifier declares (the GRDB `A2ASeenLedger`, Task 5, conforms; tests use an in-memory stub), `signingInput` + `SignedFrameParts` (Task 3).
- Produces:
  - `enum A2AChannel: Sendable { case inbox; case events }` (transport-neutral; the allowed-kinds-per-channel table is romar §5.1 — map it here, do not invent one).
  - `protocol VerifiableEnvelope { var fromProfile: String { get }; var toProfile: String? { get }; var kind: String { get }; var envelopeId: String { get }; var ts: String { get }; var deadline: String? { get }; var taskId: String? { get }; var correlationId: String? { get } }` — the transport maps its decoded envelope onto this; `deadline` is the envelope's metadata deadline.
  - `struct OutstandingRequest: Sendable { let addressee: String; let taskId: String; let correlationId: String? }` (for the `.events` binding).
  - `struct VerificationContext: Sendable { let selfProfile: String; let channel: A2AChannel; let outstanding: OutstandingRequest?; let now: Date; var allowGatewayAttested: Bool = false }`.
  - `enum PeerRejectReason: String, Sendable` — **one case per romar §5.1 reason code**, raw values exactly as romar spells them (read the list from romar §5.1/§9.1).
  - `struct PeerVerificationError: Error, Sendable { let reason: PeerRejectReason; let envelopeId: String? }`.
  - `enum FrameDecodeError: Error { case duplicateKey; case missingRequiredField(String) }` — the typed error the injected `decode` closure throws (the strict decoder is #931 Task 1's; declared here so the verifier can map it to the romar codes).
  - `protocol SeenSetStore: Sendable { func contains(peer: String, envelopeId: String) throws -> Bool; func record(peer: String, envelopeId: String, retainUntil: Date, maxPerPeer: Int) throws }` — the replay dependency the verifier declares (the GRDB `A2ASeenLedger` and a test stub both conform).
  - `struct PeerSignatureVerifier: Sendable { init(registry: PeerKeyRegistry, seenSet: any SeenSetStore, maxSeenPerPeer: Int = 10_000); func verifyAndAdmit<E: VerifiableEnvelope>(_ frame: SignedFrameParts, context: VerificationContext, domain: String = PeerSignatureDomain.a2a, decode: (Data) throws -> E) throws -> E }`.

  `verifyAndAdmit` runs romar §5's fixed order, each failure throwing `PeerVerificationError(reason, envelopeId:)` (`envelopeId` nil until the envelope is decoded): reject gateway-attested unless opted in → resolve key within the claimed principal's keyset (nil ⇒ unknown-key) → **Ed25519-verify the signing input before any decode** → `decode(frame.envelopeBytes)` (map `FrameDecodeError` to the matching romar codes) → the romar §5.1 post-parse checks in order (sender binding, kind↔channel, recipient binding by channel, `envelopeId`/`ts`/skew, deadline rules) → replay via the seen-set (`contains` ⇒ duplicate; else `record(...)` **before returning**, mapping full/unavailable to their romar codes). The verifier **never reads the envelope's self-claimed authority**; it returns the verified envelope and the consumer derives tier from the local registry. Read each threshold, the RFC-3339 grammar, and the exact code strings from romar §5.1/§6 — do not hard-code a re-derived value.

- [ ] **Step 1: Write failing tests** against a fixture `VerifiableEnvelope` conformer and real signed `SignedFrameParts` (sign with a test key; enroll its public half; back the verifier with an in-memory `SeenSetStore` stub): a well-formed inbound message is admitted; and **one test per romar §5.1 reason code** drives its rejection — including (Review Focus) unknown-key for a frame claiming `clomp` but signed by a key registered under `rune`; the events-mismatch code for an `.events` frame whose `taskId` ≠ the `OutstandingRequest`; the future-skew code at the romar threshold + 1s but admit at − 1s; the deadline-over-cap code for a message deadline past romar's cap; a non-message kind admitted with no deadline but rejected past romar's non-message bound; the duplicate code on the second `verifyAndAdmit` of the same id; and that a `FrameDecodeError.duplicateKey` surfaces as romar's duplicate-key code **with the decode closure only ever called after a valid signature** (assert the closure is not invoked on a bad signature).
- [ ] **Step 2: Run, verify they fail.**
- [ ] **Step 3: Implement** `verifyAndAdmit` in romar's order; the RFC-3339 check is a compiled regex with romar §5.1's exact grammar (not `ISO8601DateFormatter`); all time maths uses `context.now` (injected, deterministic, Invariant-7-clean).
- [ ] **Step 4: Run, verify they pass.**

**Interfaces:**
- Consumes: GRDB `DatabaseWriter`, the `JobLedger`/`PeerLedger` idiom (`JobLedger.swift:32/:108`, `PeerLedger.swift:24`).
- Produces:
  - `struct A2ASeenLedger: SeenSetStore, Sendable { init(writer: any DatabaseWriter); func contains(peer: String, envelopeId: String) throws -> Bool; func record(peer: String, envelopeId: String, retainUntil: Date, maxPerPeer: Int) throws; func prune(now: Date) throws }`.
  - `enum SeenSetError: Error { case full; case unavailable }`.
  - Migration `v37_a2a_seen`: `seen_nonces(seq INTEGER PRIMARY KEY AUTOINCREMENT, peer TEXT NOT NULL, envelope_id TEXT NOT NULL, retain_until DOUBLE NOT NULL)`, `UNIQUE(peer, envelope_id)`, index on `retain_until`.

  `record` runs in one `writer.write { db in … }`: opportunistically `DELETE … WHERE retain_until < :now`, then count this peer's rows; `>= maxPerPeer` throws `.full` (**never evict a live id**); else `INSERT`. Any GRDB error out of `contains`/`record` maps to `.unavailable` (fail-closed). Row persistence + throw-on-corrupt together satisfy "fail closed, survives restart": SQLite keeps rows across a restart, and an unreadable DB throws rather than returning empty.
