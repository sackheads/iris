# Sessions

Moved from the feature tour ([docs/features.md](features.md)), word for word (#534).

Every active conversation (not archived, not a subagent, not a job run's own hidden conversation) is a session that can see and message its peers. The Session Strip ([features.md](features.md#session-strip)) uses "session" more loosely — it also lists subagent and evaluator runs, which are somebody's delegated work rather than peers: they are never listed by `list_sessions` and cannot message anyone. You can give a session a standing role with `/role <name>` (lowercase letters, digits and `-`, 1-32 characters; `iris` and `clear` are reserved) — at most one session holds a given role at a time, so assigning an already-held role moves it there instead, and the previous holder is told and loses its skills; a role-holder can't be archived until `/role clear` releases it, and the pinned Iris holds no role. `set_session_card` also takes a name unique among active sessions (compared canonically — case, NFKC look-alikes, hidden zero-width/bidi characters and quote-style variants all fold together, so a clash can't be dodged by disguising it; `iris` is reserved, like `clear` is for roles — a clash is refused, naming the session that holds it first, then up to 19 other active names) and an optional lane; a role-holder (only) may advertise up to 5 skills — what it will do on request, with example requests — which peers see in `list_sessions` and in full via `describe_session`. `list_sessions` shows who else is running — role-holders first and never cut, then the rest most recently active first, with the pinned Iris sorted last and likewise never cut — session id, a role or `iris` marker when it has one, name, what they say they're doing, workspace, `repo@branch` when the workspace is a git repo, lane, and a status: `busy` (a turn is working), `waiting` (blocked on you, with what it waits on and for how long — a tool or job-creation approval, its subagent's or evaluator's approval, a goal contract to review, a checkpoint review or a goal judgement), or `idle` (with how long, e.g. `idle 3h`). Past the role-holders and Iris it shows at most 20 other sessions, keeping busy and waiting ones ahead of idle ones when it has to cut. `describe_session` shows one peer's full card, including skill examples. Only the status is observed by the harness; the name, lane and skills are the session's own claim about itself, advertised and unverified, the same way a self-report is not a grade. Once another session exists, it has a card, or the user has assigned it a role, a session is told its own id, title, card and role at the start of each turn, so it knows who it is without calling a tool; `set_session_card` works even with no peers and replies with what peers will see. `send_to_session` takes `to` — a session id, `role:<name>` (whoever holds it now), `name:<name>`, or `iris` — resolved at the moment of delivery, and wakes that peer with a message framed plainly as a request from another session (naming the sender's role, when it has one, as assigned by the user — the role identifies the sender and carries no authority from the user), free to decline — never as an instruction it's obliged to act on. Archived conversations are not listed and can't be sent to; a peer can't reopen one the way sending a message from you does. A job run's hidden conversation is refused the same way — nobody is reading it and every gated tool inside it fails closed, so it is neither listed nor addressable, and it cannot send either: a background run is offered none of the session tools and a send from one is refused, since delivering it would start a turn under an attended conversation's approval path. Every message gets an 8-hex msg id and belongs to a thread; the receiver's framing shows `msg <id>` and how to answer it (`in_reply_to: <id>`), and a reply is framed quoting the message it answers. `send_to_session` takes an optional `in_reply_to`: with it, `to` may be omitted (and if given must still name the original sender), the reply goes to that sender, and the id must name a message delivered to this session. `expects_reply` marks a message as a request you're owed an answer to; it shows in your own turn context as `Awaiting replies: <name> (<msgId>, <age>), …` (at most 5, then `+N more`) until a reply with a matching `in_reply_to` arrives, you call `close_request` (declared once you have an open request) to stop waiting, or the target session is archived or deleted, which closes it for you with an event line saying so — requests never expire on their own. A peer-woken chain of messages is bounded by causal hop depth rather than a shared budget: a session's depth is the depth of the last peer message that reached it, 0 once you type into it, and a send that would push the chain past `maxSessionCascade` hops (8 by default) is refused, naming the limit. Independently, each session is rate-limited to 20 sends before it must wait, then one every 15 seconds; a send over that is refused too, saying when the next one is allowed.

## Attachments

A session can hand a peer what it made — a report, a plan, a diff, a log — with `send_to_session`'s `attachments`: up to 10 per message, each a file (`{path}`) or a small JSON value (`{name, data}`, at most 64 KB). The peer sees one line per file, `Attachment: report.md (text/markdown, 12 KB) — iris-artifact://…`, and a data value inline; it opens a file with `read_file` on that `iris-artifact://` link.

- **A snapshot, not a live file.** The file is copied when it's sent, so later edits don't reach the peer. For "go fix `Sources/X.swift`", name the file in the message instead.
- **Read with the sender's own permissions.** Attaching a file asks exactly what `read_file` of it would ask; a refused or unreadable file (a directory, anything over 50 MB) means nothing is sent at all. A sandboxed session attaches a file in its workspace as the host file (a link that leads out of the workspace is refused), and a file elsewhere in its VM by reading it there, once its sandbox is running, after the same question `read_file` of `vm:<path>` asks. A session whose [agent profile](agent_profiles.md) has no `read_file` can't attach or open files.
- **Only the two sessions can open it.** An attachment opens for the conversation that sent it and the one it was delivered to (and their subagents); a link forwarded anywhere else opens nothing. That keeps attachments where they were sent, though it isn't a privacy wall between your own sessions: `read_conversation` can already read another session's transcript.
- **Peer-written, so treated as untrusted.** What an attachment says is checked by the prompt-injection guard every time it's opened, as a peer's message is. A sandboxed session that opens one also gets its own copy in its VM, at `/tmp/iris-artifacts/<sha>`, for its commands to use. A long one is shown at the same 32 KB as any tool result ([output size](tools.md#output-size)), and `read_file`'s `start_line` and `line_count` read the rest of it, so every part the peer sees has been checked whole.
- **Kept as long as it's needed.** An attachment is stored once, in `~/.iris/exchange` (named by its content's SHA-256, so the same file sent twice is stored once), while any conversation that sent or received it exists — archived ones included — and a week after the last one is deleted. Only Iris writes there, and every read checks the content still matches its name, so a file replaced behind Iris's back is refused rather than read.
- **Limits.** A session can attach 200 MB a day, and the whole store holds 2 GB by default (Settings → Advanced → Session attachments shows how much is used and sets the limit). An attachment past either limit stops the send and says which.
