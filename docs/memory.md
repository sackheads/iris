# Memory and skills

Moved from the feature tour ([docs/features.md](features.md)), word for word (#534).

Instead of trapping your workflows inside a proprietary database or cloud service, Iris uses the **[Open Knowledge Format (OKF)](https://cloud.google.com/blog/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing)** for its memory and skills layer.

*   **Markdown + YAML:** All long-term memories (`USER.md`, `SOUL.md`) and portable skills (`skills/*.md`) are stored as plain Markdown files with strict YAML frontmatter (OKF).
*   **Shipped skills stay current (#864):** Iris installs a few skills and library files of its own (the library, external-libraries, sandbox-usage, google-workspace and librarian skills, the library README and the external-libraries registry). A missing file is written at launch, so one you delete comes back. A file that is still byte-for-byte an earlier shipped version is replaced with the current text, so a correction to a shipped skill reaches an existing install. A file you or Iris edited is never touched, and a newer shipped version is not offered or logged for it; to take the new text, delete the file and relaunch. A launch that updates files writes one line to the log.
*   **Knowledge Graphing:** Iris automatically cross-links these files using standard Markdown syntax, creating a navigable knowledge graph on your local filesystem.
*   **Memory Grooming:** The background `/reflect` loop actively grooms the memory library, ensuring frontmatter is up-to-date and repairing broken cross-links.
*   **Memory Reflection:** Every 30 messages a conversation runs a reflection pass in place, where its context is. A session bound to an access profile (not the owner's own) never reflects into the owner's memory and never reports into Iris. If the profile's `memoryWrite` reaches `task`, its reflection (the automatic trigger or `/reflect`) is a narrowed one: the turn is offered a single tool, `update_profile_memory`, which rewrites that profile's own `profiles/<id>/memory.md` (16 KB at most; the file sits in the protected `profiles/` directory), and the reply stays in the conversation with no card. A profile whose `memoryRead` also reaches `task` reads that same file back into its own LATER turns (#1263, the read-back half of this loop): through the injection guard under its own `profile_memory` tag at the strictest tier, wrapped as untrusted reference data exactly like a peer's attachment, never as an instruction. A turn a guest steered never reflects into this file (#1286: the same `hasGuestInput` rule the owner's own automatic trigger follows, checked for both the automatic trigger and `/reflect`'s manual path), and a guest-steered turn never reads it back either (#1289: gated on `isGuestOriginTurn`, the same way a guest-steered turn is excluded everywhere else) — so a guest can neither write into this file nor have it read back to them through it. Two identities mapped to the SAME profile id still share this one file: what one reflects on its own, non-guest-steered turn, the other reads back on its own, non-guest-steered later turns. That sharing is a mapping-writer policy decision (tracked separately), not something this read-back gate decides, and today an operator can create it by hand-editing the mappings file. A bound session whose profile cannot write memory does not reflect at all: `/reflect` there says why nothing ran and the automatic trigger stays silent. A session a guest's message has been delivered to (a role session an MCP guest or a relay of one wrote into) does not run the AUTOMATIC reflection either, for as long as that text is in its history, which `/clear` does not remove from the model's context; for the OWNER's own reflection, `/reflect`, which you ask for, still runs there (under YOLO too: YOLO is yours to take) — a bound profile's `/reflect` does not (#1286, above). Outside Iris, what that pass changed is reported to Iris as a card naming the conversation, and the chat itself keeps only a one-line pointer ("Memory reflection ran; its report is in Iris.") — except when, during the pass, you or another session sent a message or a background subagent reported back: then the chat is left exactly as it is, so any answer stays where you can see it, and the card carries only what was said before that; a pass that changed nothing posts no card. Iris's own reflections, including the one `/new` runs, stay in Iris with no card. `/reflect` keeps its reply where you asked for it and, outside Iris, also sends the card.
*   **Project Artifacts:** Generated design docs and research notes are strictly organized into human-readable library trees (e.g., `~/.iris/library/<project_name>/`) instead of opaque UUID directories, and all artifacts enforce the OKF schema for seamless integration.
*   **JIT Prompt Injection:** Iris uses `FactStoreManager` to perform full-text searches against an embedded SQLite fact store that sits in between the working context and the static library of markdown "memories" and skills. The index uses the porter stemmer, so "use" finds "uses". Common English stopwords are dropped from the query, and matches are ranked by FTS5 BM25 over a fact's content, entity and tags, with trust and age only nudging the order; up to five go into the turn, deduplicated, each with its age ("saved 3 weeks ago"). A fact that shares only stopwords with the query never matches. Once the store holds 20 or more active facts, a match must also share a query word found in fewer than half of the active facts, or the query must name the fact's entity: in a store mostly about you and one project, your name alone does not pick out a fact. Below 20 active facts any shared word counts. The search runs on turns you typed in the main conversation. A `/goal` run searches once with its objective at kickoff and again with each steer you type when resuming it, and its reprompts carry those facts without searching again; rename and reflection turns, subagents, the evaluator, jobs and peer messages get none. Saving a fact that is already stored for the same entity (ignoring case, spacing and a trailing period) returns the existing one instead of a copy. Facts have a lifecycle: Iris can retract one that turned out wrong, supersede it with a replacement (lineage kept), or restore it, and can rate a retrieved fact helpful or unhelpful to train its trust score; that rating is the only thing that changes trust. Retrieval counts as a usage signal and records when the fact was last retrieved, never when it was saved, and a fact that has been used or rated is never evicted by age.
*   **Always-On Custom Rules:** Iris automatically loads any user-defined instruction or rule files inside `~/.iris/rules/` on startup and appends them directly to the base system prompt. This allows you to bootstrap custom behavior rules, environment notes, or stylistic constraints permanently. A rule that is personal to you can say so: start the file with a front-matter block `---`, `audience: owner`, `---` and it is left out of every turn that is not yours (a guest-steered turn, a job run bound to a narrower profile), the way USER.md and SOUL.md are. A rule without that marking still applies everywhere (what an unmarked rule does is `SkillManager.unmarkedAppliesToNonOwner`); a marking that cannot be read (an unclosed block, an unknown value) counts as `owner`. `audience: all` says the default out loud.
*   **Current Date:** The last line of the system prompt is today's date and time zone from the Mac's clock (#951), added on every turn after the cached prompt is composed, so it never freezes across days of uptime and changes the prompt once a day, which keeps the provider's prefix cache hitting. Time of day is not in the prompt; the `current_time` tool (#1093) gives the UTC and local time on demand without running `date` (whose command output would mark the session as having read outside content).
*   **Marker notice (#1209):** `USER.md` and a workspace `AGENTS.md` go to the model through the injection guard, which deletes a role marker (`system:`, `<|im_start|>`, …) from a line. When it does, the system prompt puts one line before that file's text saying markers were removed and the content is shown sanitized, so a rewrite from that view saves the sanitized version (`update_user_profile` replaces `USER.md` whole). When a model-backed guard tier has judged the file safe, a standalone `---` fence or `###` heading on a line the tier cleared reaches the model as the file has it (#1275); a role delimiter (`system:`, `### Assistant:`, `Instruction:`, a `---`/`###` glued to other text) is never restored, whatever a tier said, and with no tier, a tier that failed, or a line a tier did not clear the strip above applies. A file shown differently from the file for any reason earns a line (#1298): the marker line above when a role marker was stripped, else a second one ("some lines are shown differently from the file ... rewriting it from this view will save the altered version") when only fences or headings were, which is the common no-tier case, so with no tier an OKF `USER.md` carries it every turn (cached with the text). For `USER.md` read as the owner the line adds that `read_file` on the file returns its exact text (first-party reads are not guarded); a non-owner reader and a workspace `AGENTS.md` get no such pointer, because there a `read_file` is not faithful. A file a tier cleared, and a plain file, carry no line. A file with nothing stripped gets no line, and the line is cached with the file's text, so it costs nothing on later turns. It tells the model, not you: nothing in the app yet shows that a marker was stripped from your own file. The same notice covers reading a peer's attachment (#1267, `read_file` of an `iris-artifact://` link): it is a write-back channel too (the model can retype what it read), so a marker stripped from it gets the same leading line before the attachment's body, not cached across reads since each is its own content-addressed lookup.
*   **Held changes (#813):** A conversation that has read text from outside (a web page, a file outside Iris's own memory, rules and config, a command's output, another session's message) keeps its changes to SOUL, `USER.md`, `memory.md`, facts, skills and rules until you approve them, a background job run included. Nothing is written before then, and the review shows everything a change would write, a file write under the resolved path it lands on (with the path as the model typed it beneath, when that differs). An approved change that fails to write says so in the conversation. A chip above the composer lists each change's first line, with Approve all and Review; the pinned Iris also shows those from job runs. Settings → Security shows how many are waiting, and `iris --context-holds-report` ([docs/building.md](building.md#held-memory-changes---context-holds-report)) counts a week of them: turns with the chip, items held by kind, approved, declined, failed and pending, and the median time to decide, for the pinned Iris and for other conversations.
*   **Goal learnings (#883):** When a goal with a contract passes its gate, and at least one criterion was found not met at an earlier grade (a checkpoint's, the gate's, or your rejection), Iris saves one fact in the category `goal-learnings`: the goal's objective and the criteria that failed first and were met by the end. A criterion you waived is not named, a goal that did not pass its gate (ended at the retry cap, the grader failed, `/stop`) saves nothing, and one met on its first grade saves nothing. The text comes from the contract and the verdict values only: the grader's evidence is free text a model wrote after reading files, so it never reaches the note, and the note says which criteria flipped, not how they were fixed. It is held like any other memory write: on a goal that read outside text (a delegate's reads included) it appears in the held-changes review and nothing is stored until you approve it. It has no date and no id, so completing twice stores it once; nothing is promoted to a rule or a hook.
