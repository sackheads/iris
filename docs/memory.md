# Memory and skills

Moved from the feature tour ([docs/features.md](features.md)), word for word (#534).

Instead of trapping your workflows inside a proprietary database or cloud service, Iris uses the **[Open Knowledge Format (OKF)](https://cloud.google.com/blog/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing)** for its memory and skills layer.

*   **Markdown + YAML:** All long-term memories (`USER.md`, `SOUL.md`) and portable skills (`skills/*.md`) are stored as plain Markdown files with strict YAML frontmatter (OKF).
*   **Knowledge Graphing:** Iris automatically cross-links these files using standard Markdown syntax, creating a navigable knowledge graph on your local filesystem.
*   **Memory Grooming:** The background `/reflect` loop actively grooms the memory library, ensuring frontmatter is up-to-date and repairing broken cross-links.
*   **Memory Reflection:** Every 30 messages a conversation runs a reflection pass in place, where its context is. Outside Iris, what that pass changed is reported to Iris as a card naming the conversation, and the chat itself keeps only a one-line pointer ("Memory reflection ran; its report is in Iris.") — except when, during the pass, you or another session sent a message or a background subagent reported back: then the chat is left exactly as it is, so any answer stays where you can see it, and the card carries only what was said before that; a pass that changed nothing posts no card. Iris's own reflections, including the one `/new` runs, stay in Iris with no card. `/reflect` keeps its reply where you asked for it and, outside Iris, also sends the card.
*   **Project Artifacts:** Generated design docs and research notes are strictly organized into human-readable library trees (e.g., `~/.iris/library/<project_name>/`) instead of opaque UUID directories, and all artifacts enforce the OKF schema for seamless integration.
*   **JIT Prompt Injection:** Iris uses `FactStoreManager` to perform full-text searches against an embedded SQLite fact store that sits in between the working context and the static library of markdown "memories" and skills. The index uses the porter stemmer, so "use" finds "uses". Common English stopwords are dropped from the query, and matches are ranked by FTS5 BM25 over a fact's content, entity and tags, with trust and age only nudging the order; up to five go into the turn, deduplicated, each with its age ("saved 3 weeks ago"). A fact that shares only stopwords with the query never matches. Once the store holds 20 or more active facts, a match must also share a query word found in fewer than half of the active facts, or the query must name the fact's entity: in a store mostly about you and one project, your name alone does not pick out a fact. Below 20 active facts any shared word counts. The search runs on turns you typed in the main conversation. A `/goal` run searches once with its objective at kickoff and again with each steer you type when resuming it, and its reprompts carry those facts without searching again; rename and reflection turns, subagents, the evaluator, jobs and peer messages get none. Saving a fact that is already stored for the same entity (ignoring case, spacing and a trailing period) returns the existing one instead of a copy. Facts have a lifecycle: Iris can retract one that turned out wrong, supersede it with a replacement (lineage kept), or restore it, and can rate a retrieved fact helpful or unhelpful to train its trust score; that rating is the only thing that changes trust. Retrieval counts as a usage signal and records when the fact was last retrieved, never when it was saved, and a fact that has been used or rated is never evicted by age.
*   **Always-On Custom Rules:** Iris automatically loads any user-defined instruction or rule files inside `~/.iris/rules/` on startup and appends them directly to the base system prompt. This allows you to bootstrap custom behavior rules, environment notes, or stylistic constraints permanently.
*   **Held changes (#813):** A conversation that has read text from outside (a web page, a file outside Iris's own memory, rules and config, a command's output, another session's message) keeps its changes to SOUL, `USER.md`, `memory.md`, facts, skills and rules until you approve them. Nothing is written before then. A chip above the composer lists each change's first line, with Approve all and Review; the pinned Iris also shows those from job runs. Settings → Security shows how many are waiting, and `iris --context-holds-report` ([docs/building.md](building.md#held-memory-changes---context-holds-report)) counts a week of them: turns with the chip, items held by kind, approved, declined and pending, and the median time to decide, for the pinned Iris and for other conversations.
