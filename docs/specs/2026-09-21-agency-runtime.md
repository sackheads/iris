**Builds on:** #249 (job model and ledger spec), #252 (deliverable 1), #253 (deliverable 2). Facts about the code as it stands after #253: `.superpowers/briefs/agency-d3-facts.md` in the main checkout.

## 0. Decisions (settled 2026-09-21 morning)

Each was proposed with a recommendation; the author's answer is recorded in bold.

1. **Numeric defaults.** Per-run token budget 200,000; per-job daily budget 1,000,000; global daily background budget 3,000,000; breaker 6 runs per job per hour; retry backoff 1 m, 5 m, 25 m then pause; per-run wall-clock timeout 10 minutes; `replay` catch-up cap 5. All become `ConfigManager` keys with Settings → Advanced steppers, so the defaults only have to be sane, not final. **Accepted, on two conditions: every number is tweakable (globally in Settings and per job in `JobPolicy`), and usage is observable** — `/jobs` shows each job's tokens today against its budget and the global figure ("620k / 1M (62%)"), the breaker count for the last hour, and the retry attempt; `list_jobs` carries the same numbers; a budget or breaker pause card states the figure that tripped it. §9 is amended accordingly.
2. **What a read-only run may not call.** Recommendation: deny `write_file`, `edit_file`, `create_skill`, `schedule_job`, `register_directory_watcher`, `send_to_session`, `delegate_task`/`invoke_subagent`, any MCP tool not marked read-only, and `run_command` on the host; allow `run_command` only when sandboxed. Everything else (read, search, list, memory search, web search) stays. A denied call fails closed exactly like an approval would (§7 of the D1/D2 spec), so the ledger shows it. **Accepted.** For the record, the non-read-only run exists: a job created with `profile: mutating` keeps the full tool surface; its **commands** run in the `apple/container` VM or are refused (checked at creation and again at every fire, never falling back to the host), while every other tool — `write_file`, `create_skill`, `update_soul`, `save_fact`, the Google mutators — executes host-side as it does in any run, bounded by the user's `permissions.json` allowlist and the background fail-closed branch, so anything outside that allowlist becomes a blocked call rather than a containerised one; it is creatable in this slice (§4).
3. **"Approve and run" scope.** Recommendation: approving re-dispatches exactly the one tool call that was blocked (its persisted name and arguments), as its own tracked run in the destination conversation, and posts a follow-up card. It does not resume the model or continue the job's turn. If you want "approve and let the job finish", that is a model turn with the approval pre-granted and is a bigger, riskier design; I recommend against it in this slice. **Accepted.**
4. **Gate substrate.** Recommendation: built-in gates only need no container; a script gate requires the `apple/container` runtime and is refused at creation when it is not installed. The runtime API grows a timeout and a mount list (it had one mount and no timeout), which is a prerequisite task, not a nice-to-have. **Accepted**, and landed — amendments 11 and 13. As built (R28), "installed" is the same question a `mutating` job is asked — the runtime installed *and* sandboxing switched on — and it is asked again at every evaluation, not only at creation: when the answer has since become no, the evaluation is a gate error and the script does not run on the host.
5. **`iris --run-job`** opens your real store and uses the real model client, with approvals fail-closed, exactly like a scheduled fire. It prints the ledger row. Recommendation: yes, with a `--dry-run` that evaluates only the gate. **Accepted.** What it is for: measuring a job before trusting it — the epic's "nothing lands unmeasured": run a new job or gate on demand and read its ledger row (tokens, status, gate signal) without waiting for its schedule; feed the eval harness a gate's false-positive rate over many runs; and debug a misbehaving job from a terminal with the same fail-closed rules it has unattended. It is a measurement and debugging tool, not a way to run jobs in production.

## 1. Overview

Deliverables 1 and 2 made a job a real thing: stored, scheduled, run in a hidden conversation, recorded, reported as a card. What they left out is everything that keeps an unattended system honest over time: a job must not spend without limit, must not run concurrently with itself or thrash after a failure, must stop cleanly when it needs a human, must not wake a sleeping machine into a stampede, and must be measurable before it is trusted. That is this deliverable. Its shape is a set of **policies on the job** (`JobPolicy`), a **guard in the runner** that enforces them before, during and after a run, a **persisted blocked call** that a card can approve, **gates** that decide whether a run is even needed, and a **headless entry** to run one job on demand.

## 2. Scope

In: `JobPolicy` (overlap, catch-up, retry, budgets, timeout); the runner's in-flight tracking covering both scheduled and watcher fires; `queue`; breaker; per-run, per-job-daily and global-daily token budgets; retry with backoff and pause; sleep assertion during a run; read-only tool-surface narrowing; the persisted blocked call and "Approve and run"; gates (built-in and script) and the `.poll` trigger becoming creatable; `mutating` jobs becoming creatable; `iris --run-job`; the Settings steppers for the numbers; docs.

Out: quiet window, self-write filter, D5, D6, cost in currency (the `costMicros` column stays NULL), a job editor UI beyond the steppers.

## 3. The policy on a job

```swift
struct JobPolicy: Codable, Equatable, Sendable {
    enum Overlap: String, Codable, Sendable { case skip, queue }          // default skip
    enum CatchUp: Codable, Equatable, Sendable { case coalesce, skip, replay(cap: Int) }   // default coalesce
    var overlap: Overlap = .skip
    var catchUp: CatchUp = .coalesce
    var runTimeoutSeconds: Int = 600
    var perRunTokenBudget: Int? = nil          // nil = the global default from ConfigManager
    var dailyTokenBudget: Int? = nil           // per job per day; nil = global default
    var maxRunsPerHour: Int? = nil             // breaker; nil = global default
    var retry: Bool = true                      // failed runs retry with backoff
    init(from decoder: Decoder) throws          // decodeIfPresent everywhere (invariant 1)
}
// Job gains:
var policy: JobPolicy = JobPolicy()
var retryAttempt: Int = 0                       // 0 = not retrying; reset on a completed run
var queuedFire: Date? = nil                     // overlap .queue: one pending trigger, never more
```

Stored as one `policy TEXT` JSON column plus `retryAttempt INTEGER NOT NULL DEFAULT 0` and `queuedFire DATETIME` on `jobs`, migration `v10_job_policy` (additive; NULL policy decodes as the default). `schedule_job` gains optional `overlap`, `catch_up` (`coalesce|skip|replay:N`), `timeout_seconds` (deferred — see amendment 17), `profile` (now accepting `mutating`); `/jobs` shows the policy when it is not the default (in a column of its own rather than the trigger column — amendment 17).

## 4. The runner enforces the policy

`JobRunner` becomes the single gate for every fire, scheduled or watcher-driven; `JobScheduler`'s `firing` set is removed in favour of the runner's own `inFlight: Set<UUID>` so a watcher burst is covered too (this closes D2's deferral, ruling D2-R9).

**Before a run** (`JobRunner.admit(job:reason:now:) -> Admission`), in this order, each producing a ledger row and a card where noted:
1. Paused (`pausedReason != nil`) → dropped silently (the pause card already went out).
2. In flight → `overlap == .skip`: one `interrupted` row "skipped: previous run still in progress" (as D2); `.queue`: set `queuedFire = now` if nil, no row; when the running run finishes the runner fires once more for the queued trigger.
3. Breaker: runs started in the last hour ≥ `maxRunsPerHour` → pause with reason `"breaker: N runs in the last hour"`, one `interrupted` row, card.
4. Daily budgets: today's `totalTokens` for the job ≥ its daily budget, or today's total across all jobs ≥ the global budget → pause with reason `"daily token budget reached (<job|global>)"`, one row, card. "Today" is the local calendar day.
5. Gate (§7): built-in or script check; `gateSignal` recorded on the row; a `.poll` job whose gate says "unchanged" ends here with a `completed` row, outcome "gate: no change", **no card** (cards are for things that happened) — the row is still in `/jobs`.

**During a run:** the engine gets a per-turn budget. `processInput` gains `turnBudget: TurnBudget?` (`maxTokens`, `deadline`); the model-round loop checks it before each model call and, when exceeded, ends the turn through the existing soft-stop path with the reason `"budget: <tokens|time> exceeded"`. The runner passes `perRunTokenBudget` and `now + runTimeoutSeconds`. The run's row then finishes `failed` with that reason. Around the whole run the runner holds `ProcessInfo.processInfo.beginActivity(options: [.idleSystemSleepDisabled], reason: "Iris job <name>")` and ends it when the run finishes or the deadline passes, whichever is first — the deadline is what caps the assertion.

**Read-only narrowing:** the engine's tool-list builder takes the conversation's job profile (the runner stamps `Conversation.jobProfile: JobProfile?` on the background conversation; nullable column in v10) and declares only the `readOnly` **allowlist** for such a run (ruling R11 amended the §0.2 denylist to an allowlist of tools known to read: anything not named is refused, including every tool added later); any call that still reaches a denied tool (a stale declaration, an MCP tool without `readOnlyHint`, an unsandboxed `run_command`) fails closed like an approval and is recorded as a `BlockedCall` with `reason: .profile`. A `mutating` job's conversation is sandboxed (already enforced) and its allowlist is the user's normal one — no waiver mechanism in this slice.

**After a run:**
- `completed` → `retryAttempt = 0`; if `queuedFire != nil`, clear it and fire again.
- `failed` (LLM error, soft stop, no reply, budget) with `retry` on → `retryAttempt += 1`; attempt 1–3 set `nextFireAt = now + backoff[attempt]` (1 m, 5 m, 25 m) and the card says "retrying in …"; attempt 4 → pause with reason `"failed 3 times; paused"`, card. `blockedOnApproval` never retries (a human is needed).
- `interrupted` (app quit mid-run) → no retry; the launch sweep already marks it.
- Every pause writes `pausedReason` and a card; `/jobs resume <name>` clears `pausedReason` and `retryAttempt` and recomputes the next fire (a new `/jobs` form; also `/jobs pause <name>`).

## 5. Catch-up after sleep

`JobScheduler.tick()` on wake (and on any tick where a schedule job's `nextFireAt` is more than one cadence in the past) applies the job's `catchUp`:
- `coalesce` (default): today's behaviour — one fire now, reschedule from now.
- `skip`: no fire; `nextFireAt` = the first occurrence strictly in the future.
- `replay(cap)`: fire once per missed occurrence up to `cap`, one at a time through the runner's admission (so overlap and budgets still apply), then reschedule from the last replayed slot. The `cap` occurrences replayed are the **most recent** ones; the older ones are dropped and counted on the first card as "N earlier occurrences skipped". Replaying the oldest instead would leave the job still behind and replay another capful on the next tick, until it had run every occurrence the cap exists to prevent.
A replayed run that **fails** ends the burst as surely as a refusal does, and differently: the failure has just put the job on the retry ladder, so the row already says when it fires next and the burst's remaining slots are dropped without touching it (amendment 18). A job that went to sleep mid-retry is not a job that fell behind either — its `nextFireAt` is a backoff instant rather than a cadence slot — so it is one ordinary fire whatever its `catchUp` says.
`maxFiresPerTick` stays as the global stampede bound, and it counts fires rather than jobs: a burst the tick's cap cuts short leaves `nextFireAt` on the first occurrence it did not reach, and the next tick carries on from there. A job whose truncated burst is still running is not planned again until it ends — that row is due because the burst is unfinished, not because a second one is owed — which is the one place the scheduler's "`nextFireAt` has always moved past the fire" invariant needs help.

## 6. The persisted blocked call and "Approve and run"

D2 records only the blocked tool's name. This slice persists the call:

```swift
struct BlockedCall: Codable, Equatable, Sendable {
    let toolName: String
    let args: [String: JSONValue]     // exactly what the model sent
    let cwd: String?
    let reason: Reason                 // .approval | .profile
    let at: Date
}
```
`job_runs` gains `blockedCall TEXT` (JSON, v10); `EventCard` gains `blockedCall: BlockedCall?` and, when present, **renders the full call** — tool name and every argument (a command, a path, a URL, a body preview cut to 500 characters), never just the name — beside an **Approve and run** button and a **Dismiss** that acknowledges the row. An approval given without sight of the payload is worse than no button. **Vibecop still runs** on the persisted call when the card is built, and its verdict and reason are shown beside the button; a human click overrides a `DENY`, it does not skip the evaluation. (Review correction: the first draft skipped Vibecop "because the human approved".) `requestApproval`'s background branch and the profile denial both record the full call (the engine has `args` at the call site; `AppState.recordBackgroundDenial(call:)` replaces the name-only record).

**Approve and run** (`JobRunner.runApproved(runId:)`): loads the row and its `BlockedCall`; refuses if the job is deleted or the call was already run (`approvedAt` column, v10); creates a new ledger row (`triggerKind = "approval"`, `parentRunId` column, v10) and a fresh hidden conversation titled `"<job> · approved <tool>"`; executes the single call through `IrisEngine.executeApprovedCall(_:conversationId:)` — a new internal entry that runs `executeToolWithHooks` **directly**, so the approval is given by construction: that path never enters `AppState.requestApproval`, and there is no grant to hand out or take back (ruling R21). What the gate would have asked is asked instead by the executor itself, which refuses a `.profile` call (R13), a write into `~/.iris/config` or `~/.iris/plugins` (R10, re-checked after the hook layer), and a `run_command` with no container to run it in (R20); `runApproved` asks the same three, plus the job's profile, before it claims the call. It appends the tool result to that conversation as a system message, and finishes the row `completed` or `failed` with the result's first line as the outcome; then delivers a follow-up card to the same destination. The one-shot is durable, not in memory: `markApproved` stamps `approvedAt` in the same `UPDATE` that checks it is unset, before the call is dispatched, so a duplicated or retried dispatch, a second window and a crash mid-call all land on the same refusal. The action runs with the job's sandbox setting, and any `run_command` out of a job run is pinned to the container; a `mutating` job's approved call therefore runs in the container.

This is deliberately not "resume the job": the original turn is over, and the model's plan after the blocked call is unknowable. The card's outcome tells the user what the approved call did; if they want the job to continue, the next scheduled fire will.

## 7. Gates

```swift
enum Gate: Codable, Equatable, Sendable {
    case urlChanged(url: String)                    // HEAD: ETag / Last-Modified / Content-Length changed since last signal
    case pathChanged(path: String)                  // mtime or size-and-hash of a file, or the newest mtime under a directory, changed
    case script(command: String, mounts: [String], timeoutSeconds: Int)   // signal by stdout token, not exit code (below)
}
struct PollSpec { var schedule: Schedule; var gate: Gate }   // was `gate: String`; lenient decode maps an old string to .script(command:, mounts: [], timeoutSeconds: 60)
```
- Built-in gates run on the host with no model and no container; they read, never write. Their signal (the ETag, the mtime, the hash) is stored in `job_runs.gateSignal` and compared with the previous row's.
- A script gate runs in the `apple/container` VM with the declared `mounts` (read-only bind mounts) and `timeoutSeconds`. As built (amendment 13) it gets a container of its own per evaluation, created and removed around the one `exec`, rather than a `SandboxSessionManager` session: a session is keyed by conversation and reused, and a gate has neither a conversation nor mounts it is willing to share. **The verdict is a token on stdout's last line — `CHANGED` or `UNCHANGED` — not the exit code.** Exit codes are ambiguous here: `diff -q` returns 0 for identical and `grep -q` returns 0 for found, so any exit-code convention makes a plausible model-written gate fire every tick or never. A non-zero exit, a timeout, or a last line that is neither token is an error signal; three consecutive errors pause the job (reason `"gate failing"`). The rest of stdout (first 4,000 characters) is the gate's payload, passed through `InjectionGuard` under tag `gate_output`, and included in the run's prompt as untrusted context when the gate says `CHANGED`. `schedule_job`'s description states the token convention verbatim.
- A gate script is reviewed once, at creation or edit, and then runs on every tick unattended for as long as the job exists. It is the only model-written code in the system that executes repeatedly with no further review; the sandbox, the read-only mounts and the timeout are the mitigation, and the spec says so here so nobody widens them casually.
- Creating or editing a script gate (`schedule_job` with `gate_script`) is reviewed once by Vibecop (`toolName: "run_command"`, `inSandbox: true`); `DENY` refuses creation with the reason; `ESCALATE` asks the user in the creating conversation (the normal dialog — this is attended, the user is typing). Script gates are refused when the container runtime is not installed. **What both reviewers are shown is the script *and* the resolved read-only mount list and the timeout** (amendment 15, R33): the mounts are the durable capability being granted, and the first draft of this line — `details: <script>` — contradicted the bullet above it by naming the mounts as the mitigation and then hiding them from the one review that could refuse them.
- **Prerequisite (landed — amendment 11):** `ContainerRuntime.createDetached` and `SandboxSessionManager.run` take `mounts: [String]` and `timeoutSeconds: Int?`; the host-side `run_command` timeout that the sandboxed branch used to drop is honoured there too (a bug fix in its own right).

`.poll` jobs become creatable: `schedule_job` with `gate_url`, `gate_path`, or `gate_script` (+ `gate_mounts`, `gate_timeout_seconds`) plus a schedule. `.schedule` jobs may also carry a gate (`PollSpec` is then just "schedule + gate"; the `Trigger.poll` case stays for clarity).

## 8. `iris --run-job`

`iris --run-job <id-or-name> [--dry-run] [--json]`: parsed in `main.swift` before the SwiftUI app starts; opens the **real** store (`ConversationStore.onDisk(at: IrisPaths.default.conversationsDB)`) with a real `LLMClient`, `autoApproveTools = false`, no `HeadlessMode`, no volatile defaults (so approvals fail closed exactly as unattended); refuses if another Iris process holds the store — the app, or another `--run-job` (a lock file beside the store, released on exit; the CLI claims it by `link(2)`ing a staged pid file onto the path, so two invocations started at the same instant cannot both pass, amendment 18): GRDB's WAL would survive two writers, but `AppState` holds conversation state in memory and a CLI write behind a live app would desync the UI — so the CLI refuses rather than races. Fires through `JobRunner.fire(origin: .manual)` — admission yes, gate no — (or only the gate with `--dry-run`), waits for it, prints the ledger row (and the gate signal) as text or JSON, exits 0 for `completed`, 2 for `failed`/`blockedOnApproval`, 3 for a gate "unchanged", 1 for usage/lookup errors. The card is delivered like any run, so the Activity conversation shows it next time the app opens.

## 9. Settings, commands, and observability

Observability (§0.1): `/jobs` shows per job `tokens today <used> / <budget> (<pct>%)`, `runs last hour <n> / <max>`, and `retry <attempt>/3` when non-zero, plus a footer line with the global daily figure; the same numbers appear in `list_jobs`; every budget or breaker pause card names the figure that tripped it. The queries are the ledger sums already required for admission, so this costs nothing extra.

Settings → Advanced gains steppers for the five global numbers in §0.1 (`ConfigManager` keys `JOB_PER_RUN_TOKEN_BUDGET`, `JOB_DAILY_TOKEN_BUDGET`, `JOB_GLOBAL_DAILY_TOKEN_BUDGET`, `JOB_MAX_RUNS_PER_HOUR`, `JOB_RUN_TIMEOUT_SECONDS`), following the #208 pattern. A stepper steps from the figure its row is *showing*, so one click up from "default (6)" is 7 (amendment 18); winding one down to zero is how a number is given back to the default. `/jobs` gains `pause <name>`, `resume <name>`, and `run <name>` (fires now through admission, in-app). `list_jobs` includes `pausedReason` and the policy; `get_job_run` includes `gateSignal` and `blockedCall`.

## 11. Rulings made in this proposal (for §0 you decide the numbers; these are structure)

1. Overlap tracking moves from the scheduler to the runner so watcher fires are covered — cost if wrong: the scheduler loses a little locality; the alternative leaves watch jobs able to overlap themselves.
2. Budgets are enforced from ledger sums, not an in-memory counter — cost if wrong: one extra query per admission; the alternative loses state across launches.
3. "Approve and run" re-dispatches the persisted call and never resumes the model — cost if wrong: a job whose plan needed the call's result does not continue until its next fire.
4. A gate "unchanged" writes a row but no card — cost if wrong: a quiet job is only visible in `/jobs`; the alternative floods the Activity conversation every cadence.
5. `--run-job` refuses while the GUI is running — cost if wrong: you quit the app to measure a job; the alternative risks two writers on the store.
6. One additive migration `v10_job_policy` holds every new column — cost if wrong: none; additive.

**Amendments made during implementation** (the numbered R-rulings live in the deliverable's progress ledger; these are the ones that changed text above):

7. R11 (2026-09-21): the read-only tool surface is an allowlist, not the §0.2 denylist — §4 rewritten — cost if wrong: a genuinely read-only tool needs a one-line allowlist addition.
8. R21 (2026-09-21): the `approvedCalls` one-shot grant on `AppState` is removed and §6 rewritten to match. It was dead on the live path — `executeApprovedCall` runs `executeToolWithHooks` and never enters `requestApproval` — so the only field in the app whose contents meant "skip the approval gate" existed with no reader. The approved call is executed directly by the approved-call executor under the R10/R13/R20 checks; the durable one-shot is `approvedAt` — cost if wrong: a future caller that routes an approved call through `requestApproval` has to re-add a grant, deliberately.
9. R22 (2026-09-21): the no-host-fallback rule for a `run_command` (R20) is enforced for **any unattended run**, keyed on `isUnattended` rather than on the conversation carrying a `jobProfile`, so a subagent an unattended run delegates into — which inherits `isBackground` and not the profile — is covered too. On the ordinary fire path the refusal is recorded as an `.approval` `BlockedCall` before the approval gate is consulted, so an "Always allow" rule cannot put the command on the host — cost if wrong: a refused call the user must redo once the VM is back.
10. Correction (2026-09-21): decision 2's "always runs in the `apple/container` VM" was never true of a whole `mutating` run — only of its commands. R20's gate is scoped to `run_command`; the other tools take the host path under `permissions.json` and the unattended fail-closed branch, which turns a call outside the allowlist into a blocked call. The sentence above is rewritten to the behaviour §4 and §6 already describe; no code changed — cost if wrong: none, this is the spec catching up to the implementation.
11. R25 (2026-09-21): the §7 prerequisite has landed, so no command in this deliverable runs in the VM unbounded. `ContainerRuntime` takes `mounts: [String]` — one `--mount` per entry, rendered `type=virtiofs,source=…,target=…[,readonly]` from a `source[:target][:ro]` entry — and a per-command `timeoutSeconds` it enforces itself: at the deadline the CLI child's own children are killed first (they inherited the pipes and would otherwise hold the read open past it), then the child gets SIGTERM and, two seconds later, SIGKILL, and the call returns a timeout carrying the elapsed seconds **whether or not anything survived** — output is drained as it arrives rather than read to end-of-file, so a process nobody can signal cannot decide when the caller hears back. What the deadline bounds is what Iris waits for and reports; an in-guest process that keeps running after its `container exec` is killed is the runtime's business, and there is no flag to ask it otherwise. `run_command`'s already-clamped `timeout_seconds` is forwarded on the sandboxed branch and comes back in the host's words ("Error: command timed out after N seconds"); a deadline does not trigger the session's recreate-and-retry, which could only spend the same wall clock over again. Mount entries are refused rather than rendered when a path is not absolute (the CLI reads a relative source as the name of a volume, not a directory to bind) or contains a comma (it starts the next directive and the format has no escape); a path containing a space or an equals sign needs nothing done to it — each mount is one argv element and no shell is involved, and the CLI splits a directive at its first `=` and takes the rest verbatim. The source must also exist and be a directory — a single file cannot be bind-mounted, so a gate mounts the parent — but only the daemon can say so, and it arrives as a create failure. Mounts are part of a session's identity, checked again on the far side of the create barrier so a caller coalesced onto someone else's create does not run in their mounts — cost if wrong: a directory whose name contains a comma has to be mounted by its parent, and two callers racing with different mounts on one conversation replace each other's container.
12. R27 (2026-09-21): every `container` CLI call is drained incrementally and answers on the child's exit plus a short grace, rather than on end-of-file — so no call can be held open by a process that inherited the pipes and outlived the child, whether or not it has a deadline. `remove` and `list` carry a 60-second one anyway, because `reapOrphans()` runs `list` on the launch path and nothing there would notice; `createDetached` carries a far looser one (amendment 14), because a cold image pull is legitimately minutes. The mount agreement after the create barrier is a bounded fixed point: a call that cannot be given a container with the mounts it asked for is refused rather than run in the mounts it was handed — cost if wrong: under a contended conversation a command is refused and has to be repeated.

13. R28 (2026-09-21): gates are evaluated by `GateEvaluator`, and a `script` gate runs **only** inside the container, with its declared mounts forced read-only (`src[:dst]:ro` — nothing in the runtime forces it, so the gate does) and its timeout clamped to 5–600 s. It needs the sandbox resolvable — runtime installed and the master switch on, the same `SandboxPolicy.mutatingJobCanRun` question a `mutating` job is asked — at creation *and* at every evaluation; when it is not, the evaluation is a gate `.error`, which counts towards the three-consecutive-errors pause, and never a host run (R20/R22 hold for gates too). Each evaluation gets a container of its own, created and removed around the one `exec` and named with the `iris-` prefix so a crash's leftover is swept by `reapOrphans()`; a `SandboxSessionManager` session is keyed by conversation and reused, and a gate has neither a conversation nor mounts it is willing to share. A built-in gate is a host-side read and needs none of this: `urlChanged` is a HEAD whose ETag / Last-Modified / Content-Length are compared (a 4xx/5xx, or a response carrying none of the three, is an error rather than a permanent "unchanged"), and `pathChanged` compares a file's mtime, size and content hash, or a directory's own mtime, the newest mtime under it and its entry count. No previous signal is a *change*, not an "unchanged": the first look has nothing to compare against. A gate's "unchanged" writes a `completed` row with outcome `gate: no change`, no transcript (so the breaker does not count it) and no card; a gate error writes an `interrupted` row whose reason begins `gate error`, and the third in a row pauses the job with reason `gate failing` and a card — the pause row's reason deliberately does not carry the error prefix, so a resumed job starts counting again from zero. Editing a job's gate clears every signal its runs recorded, in `JobLedger.upsert`, because a signal is a reading taken by one gate and an ETag cannot answer for an mtime. Two bounds, not one: the script gets its declared `timeoutSeconds`, and *starting* the container gets a ceiling (300 s) of its own — `createDetached`'s own ceiling is pitched for a person at a keyboard through a cold pull (amendment 14) and is far too long for an unattended repeating caller, where a long await inside the job's in-flight mark is a job that goes quiet with no row, no card and no pause. A **cadence** fire that is not a retry consults the gate (R29, as amended by amendment 14): a retry re-runs work the gate already authorised (asking again would hear "nothing has changed since the run that failed", drop the work, write a `completed` row and jam the ladder at attempt 1), and `/jobs run` is a person who does not need a vote taken. A fire the `queue` policy held is *not* one of those: its gate was never asked — it was held before the question could be put, or held because the gate had just said nothing had changed — so it asks like any other cadence fire. Every row the gate path writes goes through the same writer and then through `apply`, so a gated job's retry-ladder and breaker bookkeeping is identical to an ungated one's. The URL gate's signal stores a hash of the validator values rather than the values, which bounds the column and keeps remote-chosen text out of `get_job_run` (which guards it in any case) — cost if wrong: one extra run after a gate is edited, and a gate script that cannot be evaluated pauses its job after three ticks rather than silently never firing.

15. R33 and R34 (2026-09-22), from the pull request's review of the gates work:
    - **R33.** The gate-script review sees the mounts. `GateScriptReview.details` composes what both halves are asked about — the script, every mount as `source → target, read-only`, and the timeout — and Vibecop and the escalation dialog are handed the same text; `BlockedCall.approvalDetails` reads a `run_command`'s `command` and nothing else, so that whole text is what goes there. §7's `details: <script>` is amended above. Showing a path is only worth anything if it is the path that will be bound, so a mount's **source is canonicalised** — tilde, `..` and symlinks, through `IrisPaths.canonicalPath`, the helper the permission layer already uses — and stored resolved, with the target left exactly as asked for (it is a path inside the container that the reviewed script was written against). At every evaluation the stored source is resolved again: anything other than itself, or a source that is no longer a directory, is a gate `.error` and no container is started, so a directory swapped for a link after the review fails closed rather than being bound unseen. Two sources are refused outright at creation rather than reviewed: `/` (by any spelling — a link to it is still it) and `~/.iris/config` / `~/.iris/plugins`, the same two directories `PermissionManager` will not let a write into. Cost if wrong: a gate on a path reached through a link records the link's target, and a user who then re-points the link gets a gate error rather than a silent re-aim.
    - **R34.** Three smaller failures of the same kind — something that could not be done and was not said. And **`reapOrphans()` spares live work**: the `iris-` prefix is shared with live sessions and with gate containers on purpose, so the sweep now skips the session table and the names `GateContainerRegistry` says are mid-evaluation. R32 (2026-09-21), on the catch-up burst: **a replayed occurrence is an ordinary cadence fire.** It carries origin `.schedule` (the job's own trigger kind), so it consults the gate, meets the whole admission order, and counts towards the breaker and both budgets exactly as the fire it stands in for would have. It follows that a replay stops at the first refusal — paused, breaker, budget, a run in flight, a gate that found nothing or could not answer — and abandons what it still owed, rescheduling from now: a refusal is a statement about the job right now, and the next occurrence a second later would meet it again. Every fire of a burst is sequential, never concurrent, because a job must not run beside itself and a task group would only have the in-flight check turn the rest of the burst into skip rows; `JobScheduler.burstsInFlight` extends that across ticks, since a burst the tick's cap truncated leaves its row due while it is still running. A **gate** refusal that leaves no card — an unchanged gate, a gate error — still records the dropped count, on the ledger row it writes or on the pause card. The walk that finds the missed occurrences is bounded (`JobScheduler.maxMissedOccurrences`, 10,000): past it the job coalesces to a single fire, because a per-minute cadence and a month of downtime is a restart rather than a catch-up — cost if wrong: a job whose first replayed occurrence trips a budget loses the other four, and has to wait for its next ordinary fire.

18. R41, R42 and R43 (2026-09-22), from the whole-branch review of the catch-up, `--run-job` and observability work:
    - **R41 — the retry ladder outranks the catch-up burst.** A replayed run that *failed* has handed the job to `apply(.retry)`, which writes the next attempt and moves `nextFireAt` to a backoff instant; the burst behind it must yield. The handler answers with the *admission*, which was `.run`, so the burst used to carry on — and four failures in one burst walked the whole 1 m / 5 m / 25 m ladder to "failed 3 times; paused" in the time it took to make them, with the user left to lift a pause that a minute's patience would have avoided. Two halves: `plan` treats a row with `retryAttempt > 0` as an ordinary single fire whatever `catchUp` says (a retry instant is not a missed occurrence, and counting it as one put the dropped figure out by one besides), and the slot loop re-reads the row between fires and ends the burst when the job is on the ladder or paused — without `abandonCatchUp`, because what the ladder wrote is already in the future and is not the burst's to move. R32's "a burst ends at the first refusal" is unchanged; this is the case where the fire was *admitted* and still ended it — cost if wrong: an ungated job whose first replayed occurrence fails loses the rest of the burst and comes back a minute later on the ladder, which is what an ordinary failed fire does.
    - **R42 — the CLI claims the lock, it does not check it.** `GUILock.acquireExclusively` stages the pid in a private file beside the lock and `link(2)`s it to the lock path, so the file is created *already holding the pid* and of two `--run-job` invocations started at the same instant exactly one passes; the documented eval-harness use (`xargs -P 4 iris --run-job …`) is precisely the shape a check-then-write lock lets through, and all four would have built an `AppState` over one store. `O_CREAT | O_EXCL` and then a write would not do: between the two the file exists and says nothing, and a loser reading it in that window is told to delete a lock that is about to be valid. A file naming a dead pid is taken over and the link retried **once** — a crash must not brick the command — and a second `EEXIST` means somebody live got there first. The takeover is a `rename(2)` of the stale file aside, never an `unlink` of the lock path: of two processes recovering from one crashed holder both unlinks succeed and the second deletes the live lock the first has just made, where exactly one rename can. The **app keeps its overwrite**: it owns the store, and a lock left by a killed build must never stop it launching. The refusal names the lock file as well as the pid, because a pid the kernel has since reused leaves nothing to wait for and no app to quit — cost if wrong: a home directory the CLI cannot write a lock into refuses the run instead of racing it.
    - **R43 — a stepper steps from the figure it displays.** `JobLimitSetting.effectiveValue` is what the Settings binding reads: a limit resting at 0 shows "default (6)" and must step to 7, not to 1. Stepping from the 0 turned the gesture that means "give it more room" into an order-of-magnitude tightening — 6 runs an hour to 1, 200,000 tokens to 50,000, a ten-minute run to sixty seconds — and in four of the five rows the only sign was the label losing the word "default". The range's floor stays 0, which is the reset: winding a stepper down past its smallest real setting lands on the value `JobLimits.resolve` reads as unset, and the row says "default" again — cost if wrong: nothing between 0 and one step of a limit can be set by clicking, which was already true.
