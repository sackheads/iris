# Agency deliverable 4½: Job grants

Status: **proposed** (2026-09-23). Closes #282. Deliverable 4½ of #187, between watches (`2026-09-22-agency-watches.md`) and the main conversation, because every later deliverable reports on what jobs did and today a job cannot do anything. Argued from `docs/agency/agency.md` ("Sandbox always. A `mutating` job runs in the `apple/container` VM, full stop. A waiver widens the tool allowlist inside the container; it never drops isolation") and from the runtime spec's Correction 10 (`2026-09-21-agency-runtime.md` §11): the VM rule was only ever true of a job's *commands*; `write_file`, `read_file` and the other native tools take the host path behind `permissions.json`. This deliverable is the waiver the epic names, with a shape.

## 0. Decided

Each decision names its default and why; the cost of being wrong is what a reviewer should weigh.

1. **A grant is the person's, made once, at creation, through the tool call.** `schedule_job` and `register_directory_watcher` take `mounts` and `network`; the model passes them from what the person asked for in an attended conversation, the result echoes them verbatim, and re-scheduling or re-registering the same job with a different grant replaces it (omitting `mounts` removes it). No confirmation card. *Why:* the person asked, in a conversation they are watching; a second click is a paraphrase check, and the owner's call is functionality first. Job creation from an unattended run stays refused (`jobCreationTools`), so a grant can never be written by a job. *Cost if wrong:* the model widens a grant the person phrased narrowly; the result sentence and the `/jobs` line are where they would see it, and the fix is a re-schedule.
2. **A grant is directories plus a network bit; nothing else.** `mounts` is an ordered list of `source[:target][:ro]` entries — read-write unless `:ro` — with the grammar and the refusals `gate_mounts` already has; `network` is a Bool, default `false`. No per-command allowlists inside the container, no secrets. Credentials reach a job only as a read-only directory the person names (a deploy-key folder, `~/.config/gh`, a `.netrc` directory). *Why:* two knobs the person can read back in one line; the container's own boundary does the rest. *Cost if wrong:* a job that needs one secret has to be handed the directory that holds it, which is wider than the secret; a later slice adds per-job Keychain secrets as env vars.
3. **Only a `mutating` job may carry a grant.** A read-only job created with `mounts` or `network` is refused with a sentence saying why. *Why:* read-only runs are read-only because their container has no mounts (docs/jobs.md, Profiles) and their tool surface is the allowlist; a grant on one would make that paragraph false in two ways at once. *Cost if wrong:* a read-only job that wanted a read-only mount for `run_command` has to become `mutating`; acceptable, because a mount is exactly the thing that makes a run more than read-only.
4. **Commands run in the VM with the grant's mounts, and that is the approval.** For a granted run, `run_command` is allowed unattended when — and only when — the conversation resolves as sandboxed (R20/R22 unchanged: no runtime or sandboxing off means refused, never host). *Why:* the mounts and the network bit are the containment; a per-command rule would be a second copy of the same decision in a form nobody can read. *Cost if wrong:* a granted job can run any command the container can, against the mounted directories, on the network if allowed. That is the feature.
5. **File tools stay on the host and are allowed only inside the grant.** `write_file` is allowed unattended when its resolved, canonicalised path is under a read-write mount's source; `read_file` under any mount's source. Neither is re-implemented inside the container. *Why:* mounts are identity-mapped, so a host write at `/Users/me/proj/out.md` is the same bytes on the same disk the container would write through the mount; keeping the host implementation keeps atomic writes, the self-write filter (§4 of the watches spec reads host paths) and the R10 protected-directory check exactly as they are. *Cost if wrong:* "the VM rule" remains a rule about commands, as Correction 10 already says; a reviewer who wanted a purer sentence gets the same blast radius and one less subsystem.
6. **The first read-write mount is the run's working directory** and the hidden conversation's `workspacePath`. If any entry is read-write, the first entry must be one, so the working directory is never in doubt; a grant with no read-write mount gets `/` as today. *Why:* one rule feeds `-w`, relative-path resolution in `write_file`, the AGENTS.md loader and the per-workspace sandbox file. *Cost if wrong:* a job whose two read-write trees are peers has to name the one it works in first; the result sentence says which was chosen.
7. **Network off is an internal network, not the absence of one.** Measured on this machine (`container` CLI 1.1.0): `run --network <name>` takes a network name and has no `none`; `network create --internal <name>` makes a host-only network with no route out. A granted job with `network: false` is attached to an Iris-owned internal network (`iris-isolated`, created on demand) with `--no-dns`; `network: true` uses the default network; a job with no grant keeps today's container on the default network (no behaviour change outside the feature). `network: true` with no mounts is a valid grant — commands may reach the network from a mount-less container, and the gate then covers only `run_command`. If the isolated network cannot be created the fire fails closed with the reason on the row. *Why:* the only "off" the runtime offers. *Cost if wrong:* a future CLI that drops `--internal` breaks isolation loudly (the create fails) rather than silently (the fire fails, the row says why).
8. **Grants are re-checked at every fire and at every approved call**, the way gate mounts are: each source must still canonicalise to itself and be a directory, and `SandboxPolicy.mutatingJobCanRun` is asked again. *Why:* a grant is a claim about the disk made once; the disk moves. *Cost if wrong:* a renamed source fails the fire with `grant source unavailable: <path>` and the job pauses when the existing retry ladder is exhausted (three retries, so the fourth consecutive failure), rather than through a new ladder.
9. **The grant is matched on the real path, never a lexical one, and `..` is refused outright.** Found in pre-review: `IrisPaths.canonicalPath` collapses `..` lexically *before* resolving symlinks, while the kernel follows a symlink before the `..` after it — so `<mount>/link/../x`, with `link → ~/.iris`, is judged inside the mount and written outside it (reproduced). A granted run's `write_file`/`read_file` path is refused if any component is `..` after tilde expansion (a model never needs one inside a grant), and the match uses a component-wise real path: `realpath(3)` of the deepest existing ancestor of the *unstandardised* components, then the remaining components appended. The same helper hardens `isUnderProtectedWriteDir` (R10) for every caller, attended or not. *Why:* an allow must be computed the way the kernel will act. *Cost if wrong:* a legitimate `..` inside a mount is refused with a sentence and falls to the allowlist; nobody loses a write they could not have phrased without `..`.
10. **A granted run's container mounts are a pure function of its grant, and `set_workspace` is refused unattended.** Found in pre-review: `set_workspace` has no unattended refusal and is not approval-gated, so a granted run could re-point its workspace to `~` and have the next auto-allowed command see home — `~/.iris` included — mounted read-write. The workspace mount is `grant.workingDirectory`, never the conversation's current `workspacePath`; and `set_workspace` is refused for every unattended conversation (a run and the subagents it delegates into) with `Not run: a background run cannot change its workspace; widen the job's grant instead.` The only way to widen is a re-schedule from an attended conversation. *Why:* the grant is the boundary; nothing a run does may move it. *Cost if wrong:* an ungranted mutating job loses the mid-turn `set_workspace` path docs/jobs.md described, which only ever bought it a mount whose commands still needed approval; a grant replaces it.
11. **An explicit `network: false` on a mutating job is a grant, mounts or not.** `JobGrant(mounts: [], network: false)` isolates the container and reads `Grant: no mounts · network off.`; only a call that names neither `mounts` nor `network` leaves the job ungranted on today's default-network container. On a read-only job an explicit `false` is nothing to record. *Why:* a person who said "network off" must get it. *Cost if wrong:* none found.

## 1. Model

`JobGrant` is a `Codable` value stored **inside `policy`** as `grants`, so there is no migration and an older build reads a granted job as an ungranted one (the policy decoder ignores unknown keys — the safe direction; note that an older build re-saving that job would drop the grant, which is the same fate every unknown policy key has today and is documented):

```swift
struct JobGrant: Codable, Equatable, Sendable {
    var mounts: [ContainerMount]   // ordered; ContainerMount becomes a struct (source, target, readOnly) — see below
    var network: Bool              // default false
    var workingDirectory: String? { mounts.first(where: { !$0.readOnly })?.source }
}
```

`JobPolicy.grants: JobGrant?` decodes leniently: absent → nil; a blob that does not decode → nil **and the job still loads** (invariant 1). `ContainerMount` is today a caseless namespace of two helpers (`argument(for:)`, `hasReadOnlyFlag`); it becomes a struct with `source`, `target`, `readOnly`, an `init(parsing:)` that applies the same grammar and refusals, and `Codable` as the string form `source[:target][:ro]` — the same string the tool accepted, so `/jobs`, the result and the row all show one spelling. The two helpers stay, so every existing caller compiles unchanged.

Refusals at creation, in this order, each its own sentence (all reuse `GateEvaluator.mountRefusal` and `WatchRoot.refusal` where the rule already exists): a grant on a read-only profile; a malformed entry (`ContainerMount.invalidMount`'s reasons: parts, empty, relative, comma); a source that does not exist or is not a directory; `/`, a volume root or any mount point, the home directory, or a path that is or contains `~/.iris` (read-only included — the memory tools write there outside every filter); a read-only first entry when a read-write entry follows it; the same source twice. Nested entries are allowed (the inner entry's mode wins for paths under it) and the result says so. Paths are the host's: in a `write_file`/`read_file` call the path is the mount's *source*; inside a command it is the *target*. Entries without a target are identity-mapped, which makes the two the same and is the form the declaration recommends.

## 2. Execution

**The container.** `JobRunner.openConversation(for:titled:sandboxed:)` stamps the hidden conversation with `workspacePath = grant.workingDirectory`, `mainAgentSandbox = .sandboxed` (as today for mutating), and a new `sandboxGrant: JobGrant?` on `Conversation` (persisted column `sandboxGrant TEXT`, lenient; nil for every other conversation). `SandboxSessionManager.run` already accepts `extraMounts` and already recreates a container whose mount set disagrees; `ToolExecutor.runCommand` derives the container's whole mount set from the grant when one is present — the working directory from `grant.workingDirectory`, never from the conversation's `workspacePath` (§0.10), the rest as `extraMounts` — and from the workspace as today when there is none. `CLIContainerRuntime.create` gains `network: NetworkMode` (`.default` or `.isolated(name)`) rendered as `--network <name> --no-dns` for isolated, and `ensureIsolatedNetwork()` runs `container network create --internal iris-isolated` when `container network ls --format json` (measured: an array of objects with `id` and `configuration.name`, both `"default"` for the built-in) does not list it; a create whose stderr says `already exists` is treated as success (measured: the CLI reports `Error: network <name> already exists` for a duplicate), so two racing creates cannot fail a fire; a listing that fails is itself a failure and the fire fails closed. Create argv for a granted job therefore reads

```
run -d --name iris-<id> --mount type=virtiofs,source=/Users/me/proj,target=/Users/me/proj
  --mount type=virtiofs,source=/Users/me/.config/gh,target=/Users/me/.config/gh,readonly
  --network iris-isolated --no-dns -w /Users/me/proj <image> sleep infinity
```

and is pinned by a fake-runtime test per grant shape.

**Lifecycle.** `closeSession` now also calls `SandboxSessionManager.endSession(id)` for the run's conversation, which the runner never did (today a run's container lingers until the idle reaper or the launch sweep). Approve-and-run opens its one-call conversation with the same grant. Subagents a granted run delegates into inherit `sandboxGrant` with `isBackground` and `workspacePath` (`SubagentManager` already copies the latter two), so a delegated command runs under the same mounts and network, never wider.

**Drift.** At fire and at approved-call time, before the container is created: every source must canonicalise to itself and be a directory (`GateEvaluator.mountDrift`'s rule); a miss fails the fire with `grant source unavailable: <path>` — a `failed` row that walks the existing retry ladder and pauses when it is exhausted. `mutatingJobCanRun` is asked as today; sandboxing off fails with `sandbox unavailable` as today, grant or no grant.

## 3. The gate

`AppState.requestApproval`'s background branch gains one step **before** the exact-match allowlist and **after** nothing — the fail-closed shape stays first:

```
background conversation:
  if isProtectedWrite → refuse (R10, absolute; asked here explicitly, before any grant is read)
  if let grant = conversation.sandboxGrant, grant.allows(toolName, details, cwd) → allow
  if permissions.isAllowed(..., isBackground: true) → allow
  record BlockedCall(.approval) → refuse
```

`JobGrant.allows` is pure and tested on its own: `run_command` → `true` (the sandbox question is asked by the R20 check that precedes approval in the dispatcher and by `executeApprovedCall`; a grant never reaches a host command); `write_file` → the path, resolved against `cwd` with `ToolExecutor.resolvePath`, refused if any component is `..`, and taken to its component-wise real path (§0.9: `realpath` of the deepest existing ancestor of the unstandardised components, remaining components appended — so a new file under a mount resolves to the mount and a symlink is followed where the kernel follows it), is under a read-write source by path-component prefix (`/proj` does not cover `/project`), compared case-sensitively — this is an allow, so a differently-cased spelling falls through to the allowlist rather than being granted — with the innermost matching entry deciding; `read_file` → under any source. Everything else → `false`. R13 is untouched: a read-only profile refuses before approval is asked. `set_workspace` is refused for any unattended conversation (§0.10), in the dispatcher beside the `jobCreationTools` refusal, so no run can move its own boundary.

What this does not change, stated so the docs can: the tools that never needed approval (`save_fact`, the Google mutators, MCP tools) are neither widened nor narrowed; the skill and memory tools stay refused unattended; the self-write filter is fed exactly as before, because writes still happen on the host at the granted path; files a *command* writes in the container are still invisible to it, so a job that writes into a watched folder should use `write_file`, and #283 sizes the breaker for watches. The `approvalOffer`'s `inSandbox: job.profile == .mutating || …` hint to Vibecop, which today calls a mutating job's host `write_file` sandboxed, is corrected to `toolName == "run_command"` while this code is open.

## 4. Tool surface

`schedule_job` gains `mounts` (`"Directories the job may use, as '/host/dir', '/host/dir:ro' or '/host/dir:/path/in/container'. Read-write unless ':ro'. The first read-write one is the job's working directory. Mutating jobs only. Recorded as the directory each path resolves to; the whole filesystem, the home directory, volume roots and Iris's own directory cannot be mounted."`) and `network` (`"true lets the job's commands reach the network from inside the VM; default false, which attaches the VM to a host-only network. Mutating jobs only."`). `register_directory_watcher` gains the same two plus `profile`, since a watch that writes needs to be mutating; the watched folder is **not** implicitly in the grant. The long description's sentence "a job whose work needs approval stops and says so" gains "unless the job was created with a grant that covers it". The result sentence, on success, ends with the grant: `Grant: read-write /Users/me/proj (working directory) · read-only /Users/me/.config/gh · network off.`

Replacement, spelled out because `schedule_job` never replaced before (a name collision is suffixed `-2`): an explicit `name` that names a job **created in the same conversation** replaces it — id, `createdAt`, destination and run history are kept; schedule, prompt, profile, policy and grant are taken from the new call, so a call without `mounts` removes the grant. Any other collision still suffixes. A re-registration of a watch by the same conversation and path replaces its grant with exactly what the call names, while the watch's other optional arguments keep their stored values as today; the effective profile is the given one or the stored one. A `mutating` watch is refused without the VM, with the sentence `schedule_job` uses. `list_jobs` returns `grants` as stored (null when absent).

## 5. Observability

- `/jobs`: the policy column shows `grant` for a granted job; beneath the table, one paragraph per granted job: `` `deploy` — read-write /Users/me/proj (working directory) · read-only /Users/me/.config/gh · network on ``.
- The run card's metadata line gains `network` when the run had it.
- A card for a call blocked **outside** the grant names the nearest granted directory: `needs approval: write_file outside the grant (nearest: /Users/me/proj)`, so the person can widen once instead of clicking every time. The nearest directory travels on the `BlockedCall` (lenient, nil for ungranted runs) so the row, the card and the transcript notice agree.
- The fire-time refusals have their own reasons: `grant source unavailable: <path>`, `isolated network unavailable: <detail>`.

## 6. Tests

All headless, per AGENTS.md invariant 7: fake runtime, temp `IrisPaths`, in-memory store, no real containers, no `~/.iris`.

- `JobGrantTests`: argument parsing; each refusal in §1 by name; nested entries; the result sentence; replace and remove on re-schedule; lenient decode (absent, malformed → nil, job still loads); `ContainerMount` round-trips through its string form.
- `JobGrantGateTests` (pure `allows`): inside, boundary (`/proj` vs `/project`), outside, `..` walking out, a symlink from inside a mount to a protected directory (resolves outside → refused), `<mount>/link/../x` with `link → ~/.iris` (refused by the `..` rule and, with the `..` removed, judged by the real path — both tools, and through `requestApproval` asserting the R10 branch records it), `set_workspace` from a background conversation refused, a granted run whose `workspacePath` was changed still mounting only the grant, relative path against the working directory, read under a read-only mount, write under a read-only mount refused, innermost entry wins, `run_command` true, everything else false. Then through `requestApproval`: R10 first; grant miss falls to the allowlist; read-only profile untouched.
- `JobRunnerGrantTests`: the fire stamps workspace, grant and pin on the conversation; drift fails with the exact reason and walks the ladder; `endSession` at close; the approved call reopens with the same grant; a delegated subagent inherits it.
- `ContainerRuntimeTests`: create argv per grant shape including `--network iris-isolated --no-dns`; `ensureIsolatedNetwork` parses `id`/`configuration.name`, creates once, treats `already exists` as success, and fails the fire closed on a failed listing or create.
- `JobGrantTests`: explicit `network: false` with no mounts on a mutating job is a grant (`no mounts · network off`), and nothing on a read-only one.
- Rendering: `/jobs` grant line and policy column; `list_jobs` JSON; card `network`; the outside-the-grant notice.
- Restated by name and kept green: the fail-closed background branch, R10, R20/R22, `SelfWriteHookTests.everyDeclaredToolIsClassified`, `ToolSurfaceTrimTests`.

## 7. Delivery

One PR after a spec review and a plan, or two if the plan's size says so (behaviour: §1–§3; surface and docs: §4–§5). On-screen before opening, from fresh conversations with cleanup after: (1) a mutating job with a read-write temp folder and network off whose prompt writes a file and runs `git init && git status` → one completed run, no approval card, the file on the host; (2) `curl https://example.com` inside it fails; re-scheduled with `network: true` it succeeds and the card says `network`; (3) a `write_file` one directory above the mount → `blockedOnApproval`, the card names the nearest granted directory; (4) a watch on the same folder absorbs the job's write as an own write; (5) delete the folder → `grant source unavailable`, paused when the retry ladder is exhausted; (6) `/jobs` shows the grant line and column. The PR body carries the real create argv from the runner's log and both curl results.

Docs: `docs/jobs.md` gets a Grants section, its Profiles paragraph rewritten (host writes are "behind the allowlist or the job's grant"), and its paragraph about a mutating run giving itself a workspace mid-turn deleted (§0.10); the runtime spec's §0.2 and Correction 10 get an amendment naming this deliverable; `docs/agency/agency.md` gains this deliverable between 4 and 5 and its "Sandbox always" line gains "the waiver is the job's grant (`2026-09-23-agency-job-grants.md`)"; README's jobs bullet names grants.

## 8. Not in this deliverable

Per-job secrets from the Keychain as environment variables; unattended memory and skill writes; grants on read-only jobs; per-command allowlists inside the container; container-side `write_file`/`read_file`; a UI for editing a grant (re-schedule is the edit).
