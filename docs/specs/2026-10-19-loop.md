# /loop (#190)

**Status:** spec for PR 1, iris-dev-2, 2026-10-19.  Brian picked this ("both yes, and /loop"), and the planner's rulings are folded in below.  PR 2 adds the self-paced mode.

## The boundary with jobs

A **job** runs in a hidden conversation of its own, with nobody there.  It's unattended: `hardStrip`, refusals and grants stand in for approvals, and it reports through an event card.  [Delivery never wakes a model turn](../jobs.md): waking the model on every run "would turn a five-minute schedule into a five-minute agent loop".

**/loop is that agent loop, on purpose, for one visible conversation you opt into:**
- the same history, role, workspace and agent profile;
- you can talk to it between iterations and change what it does (#190's PR Minder);
- it can reach peers with `send_to_session`.

So `/loop` never creates a `Job` row, never uses `JobScheduler` or the run ledger, and never runs unattended.  A design that needs any of those is a job, and belongs in `schedule_job`.

**The decision test:** do you want to talk to it?  `/loop`.  Should it run with the app closed, or with no one watching?  A job.

## The anchor: `/goal`'s reprompts

Iris already has a self-prompting loop in a visible conversation: `/goal`'s reprompts.  `/goal` loops until done; `/loop` loops on a cadence.  A loop tick is the same kind of turn as a goal reprompt, on the same machinery:

| | `/goal` reprompt | `/loop` tick |
| --- | --- | --- |
| **Scheduled by** | `scheduleReprompt` → `GoalLoopControl.setReprompt` | `armLoopTick`, on a slot of its own (`IrisEngine.loopTicks`).  Not the goal's: a pending goal follow-up holds every arrival until it runs, and a tick waits up to a day.  Stop cancels a waiting or running tick; any other turn (typed, a peer's, a subagent's post-back) takes a waiting tick's place, and its end arms the next |
| **Principal** | `.main` | `.main` |
| **Attended** | yes: the conversation's own `isBackground`, so prompts go to the dialog and Vibecop | yes, the same |
| **Facts** | `goalFacts: .carry`, with no fresh search | `.carry`, the same.  With no goal there's nothing carried and no contract objective to search, so a tick gets no facts at all; the person's own turns in the conversation still search as usual |
| **Delay** | `Task.sleep(repromptDelay)`, 1.5 s | `UptimeWait`: a `DispatchQueue.asyncAfter` on uptime (Invariant 4, #608), the loop's interval, cancellable |
| **Source and framing** | `"System"`, framed as `System Event [System]: … + systemEventAnalysis` | `"Loop"`, its own frame, without the "briefly acknowledge it" suffix (#475 showed models take that as an exit) |
| **Re-armed** | at a turn's end, while `activeGoal` is set | at a turn's end, while a loop is set, not paused, and has ticks left |

**The `"Loop"` source:**
- `isTrigger` requires `"System"`, so a loop prompt that happened to start with a trigger prefix (`System Event [Rename Trigger]` and the like) can never act as one (#581).
- `retrievesFacts` requires `"UI"`, so a tick never searches facts, as a reprompt doesn't.

**What isn't shared:** a `/loop` and a `/goal` can't run in the same conversation at once.  Starting either while the other is active is refused, with a sentence naming the active one.  So a turn's end never has to choose between a reprompt and a tick.

## Pacing

- **PR 1, fixed interval:** `/loop <interval> <prompt>`, for example `/loop 10m check my open PRs`.
  - The interval is `30s`, `5m`, `2h` and the like.
  - It's clamped to between 1 minute and 24 hours, and a value outside that range is refused, saying the range.
- **PR 2, self-paced:** `/loop <prompt>`, where the model calls `schedule_next_tick(delay_seconds)`.
  - **Gated (Invariant 6):** declared only while the conversation has a self-paced loop, to the main agent only.  It's in `StickyTools.eligible`, refused at dispatch without a self-paced loop, and never offered to a job.
  - **The delay** is clamped to 60 s - 1 h, and the result says what was applied.
  - **No call in a turn** means the next tick is 20 minutes away.  The loop carries on rather than stopping, because a missed call is the model's lapse, not a request to end, and the tick cap still bounds it.
  - **The first tick** comes a minute after `/loop`, so the model sets its pace from the start.
  - **What the tool says about itself:** it sets the delay only.  It never ends the loop; the person does, or the cap.
  - A first word that starts with a digit but isn't an interval (`10mn`) is refused as a typo, not read as a self-paced prompt.
  - **Profiles (#465 part 2):** a flow tool, so a profile's `tools:` list never narrows it.

**The timer:**
- It runs on `DispatchQueue.asyncAfter`, whose `DispatchTime` is uptime, so time the Mac spends asleep doesn't count.  It runs from the end of the previous turn.
- There's only ever one pending tick, so ticks missed during a sleep coalesce into one on wake.

## Forks, as ruled

- **Arrivals don't wait for a tick.**  A peer's message, a background subagent's post-back or a watcher event runs its turn at once, as in a conversation with no loop, and the next tick is an interval after that turn.  So a busy conversation ticks less often, never more.
- **A hook that blocks a turn** (a blocking BeforeAgent, ToolSelection or PreCompress hook) ends that turn before its end arms the next tick.  So the loop stops arming, visibly: the chip says it's stopped and offers Resume.  That's on purpose, since a hook that refuses the turn shouldn't be retried on a timer.
- **A. A tick while a turn is running, or with an approval pending:** it's skipped, and nothing queues; the next tick is an interval away (and the running turn's end re-arms it anyway).  An approval prompt belongs to a running turn, so a loop waiting on one stalls visibly; it doesn't pile up.
  - Ticks run attended: a step that needs approval waits for the person, as under `/goal`, and a loop gets no job grants.  Brian, 2026-10-19: "1: a" (the planner's ruling 1).
- **B. Stop:** it matches what Stop does to a `/goal` today.  (The chip's button says **End loop**, since the composer's Stop keeps it.)
  - Stop (Esc, or the button) cancels the running turn and the pending tick, but keeps the loop, just as it keeps `activeGoal`.  The loop re-arms when your next turn ends, or when you press **Resume** on the chip.
  - `/loop stop` ends the loop, and so does `/stop`, which also ends a goal.  Both, and Pause, drop a waiting tick; a tick already running finishes.
- **C. Restart:** the loop persists with the conversation (`Conversation.loop`, `decodeIfPresent`, its own column).  It comes back **paused** on launch: one click on **Resume** re-arms it.  Nothing a person stopped looking at fires at launch.
- **D. The spend bound:** each loop has a tick cap.
  - The default is 50, set in Settings → Advanced → Agent Limits → Loop tick limit.
  - The chip shows the ticks left.  Re-running `/loop` renews the cap.
  - Reaching it ends the loop, with one line saying so.
- **E. The pinned Iris conversation:** `/loop` is refused there in v1 (Brian, 2026-10-19: "2: a", the planner's ruling 8).  Iris is the conversation your memory and `/new`'s rotation work from, and a loop would fill it with ticks.  (Not reflection: ticks don't count toward it, below.)  The refusal also covers a loop found on Iris at load, which `sanitizeLoaded` clears.
- **F. Growth:** each tick appends a turn, and **Iris has no history compaction** (a search of `iris.swift` and `AppState` finds none; `/new`'s rotation in Iris is the only summariser).  So every tick resends the whole conversation so far, and a tick costs more as the conversation grows.  The cap is the bound, which is why it's on by default.
  - The `/loop` reply and `docs/slash_commands.md` say this.
  - A tick that finds nothing new is asked to say so in one line, which keeps its turn short.
  - A compact rendering for such ticks is left for later.

**Reflection:** ticks don't count toward the 30-message reflection trigger.  `messageCountSinceReflection` advances in `AppState.startTurn`, which runs for a message the person sends and for each queued message drained into a turn (a peer's `send_to_session` included).  A tick calls `processInput` directly with source `"Loop"` and never goes through it.  That's deliberate: a loop's ticks aren't conversation the person is having.  (A peer answering a loop's messages still counts, as it does today without a loop.)

## UI

- **A loop chip** in the composer stack, capped like the goal chips (Invariant 8): "Looping every 10m · 37 ticks left", the next tick's time, and **Pause**, **Resume** and **Stop**.
- **A sidebar row** gets a secondary "↻ every 10m" line (or "↻ paused").

## Out of scope

- Cross-session negotiation beyond `send_to_session` (#185).
- Loops in subagents or jobs.  A loop needs a person to talk to, so `/loop` is refused in a background or subagent conversation.

## Persistence (Invariant 1)

- **Model:** `Conversation.loop: ConversationLoop?`, holding an `id`, the prompt, `intervalSeconds`, `ticksLeft`, `cap` and `paused`.  The id is checked when a tick fires, so a tick armed for one loop never runs in a replacement.
- **Read:** `decodeIfPresent`, plus a `CodingKeys` case.
- **Store:** a `ConversationStore` migration adding a `loop` column (JSON text), in both `upsertMetadata` branches and in `loadAll`.  A value that doesn't decode drops only the loop, as a soft loss.
- **Load:** `sanitizeLoaded` pauses every loaded loop, and clears one on the pinned conversation (or a background or subagent one, which can't hold a loop either).
